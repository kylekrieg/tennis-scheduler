This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm install                                    # zero native build deps — see "Database" below
cp .env.example .env                           # then fill in ADMIN_PASSWORD_HASH at minimum
node src/scripts/hash-admin-password.js "pw"   # generate ADMIN_PASSWORD_HASH for .env
node src/db/seed-example.js                    # loads the example 9-player/17-week roster into data/tennis.db
npm run reset-data -- --confirm                # wipes all player/season data (keeps admin logins + settings), backs up first
npm start                                      # or: npm run dev (identical — no watch/build step)
npm run test:scheduler                         # runs src/scheduler/engine.test.js directly with node, no test runner
```

There is no build step, bundler, or linter configured — it's plain CommonJS Node, run directly. `npm start`/`npm run dev` are identical; there's no file-watching dev mode.

To run a single check while iterating on the scheduling engine, just run `node src/scheduler/engine.test.js` (it's a plain script with `assert` calls, not a test framework — add new cases as additional `{...}` blocks in that file following the existing pattern).

The app requires Node >= 22.5 because it uses the built-in `node:sqlite` module (see below); check with `node --version` before debugging anything that looks like a DB issue on an older Node.

## Architecture

### Database: `node:sqlite`, not `better-sqlite3`

`src/db/index.js` deliberately uses Node's built-in `node:sqlite` (`DatabaseSync`) instead of `better-sqlite3`. This was a conscious tradeoff to make `npm install` have zero native compilation, which matters most on a Raspberry Pi target. `src/db/index.js` wraps `DatabaseSync` in a thin `prepare().run/get/all` + `transaction()` shim so the rest of the codebase reads like typical better-sqlite3 code.

Schema lives in `src/db/schema.sql` and is applied via `CREATE TABLE IF NOT EXISTS` on every boot. Because that doesn't add columns to an already-existing table, `src/db/index.js` also runs a small `ensureColumn(table, column, definition)` guard after loading the schema — this is the only migration mechanism in the app. When adding a new column to an existing table, add both the column to `schema.sql` (for fresh installs) *and* an `ensureColumn(...)` call in `db/index.js` (for databases that already exist), or existing deployments will break.

### The scheduling engine is pure and separate from the DB

`src/scheduler/engine.js` has zero dependencies on the database or Express — it's a pure function (`generateSeasonSchedule`) that takes plain JS objects in and returns plain JS objects out. This is deliberate so it can be unit-tested directly (`engine.test.js`) without spinning up a DB. It does three things in sequence:

1. **Feasibility + assignment** via max-flow (`solveAssignment`): source → player nodes (capacity = target games) → week nodes (capacity = players-per-week, reduced per-week if the week is understaffed — see below) → sink. If max-flow doesn't saturate *even after* accounting for understaffed-week reductions, it's genuinely infeasible, and the code inspects the residual graph to produce specific, actionable conflict messages (which player can't hit their target, or — as a fallback — a min-cut description of a combined conflict) rather than silently producing a bad schedule.
2. **Partner-variety optimization** (`optimizePartnerVariety`): a bounded simulated-annealing pass that swaps *which week* two players attend (never changing target counts or violating blackout dates) to spread teammate pairings evenly, using a deterministic seeded PRNG so results are reproducible for a given input. Weeks reduced to 0 players are excluded from swap candidates entirely (nothing to optimize, and swapping a nonexistent player would corrupt another week's roster).
3. **Ball duty** (`assignBallDuty`): a deficit-based greedy pass so ball duty lands proportional to each player's share of total games, counting only weeks that actually have a match.

`src/services/scheduleRun.js` is the glue layer: it reads a session's roster/blackout dates from the DB, calls `generateSeasonSchedule`, and persists the result. The critical invariant it maintains: **locked weeks (`weeks.locked = 1`, meaning already played) are never touched or recomputed** — only unlocked/open weeks are ever regenerated. This means `session_players.target_games` represents the target for whatever weeks are still open at the time "Schedule these players" is clicked, *not* a fixed season-long total — after a mid-season roster change, the admin is expected to re-enter targets that sum to `(open weeks) × players_per_week`, and the roster edit UI (`session_form.ejs`) has a live JS helper that mirrors this exact calculation (`countMatchingWeeks`, kept in sync with `scheduleRun.js`'s `datesForDayOfWeek`) so the numbers can be checked before saving.

### Understaffed weeks: scheduled with who's available, flagged, doesn't block the season

Originally, if blackout dates left a single week without enough available (non-blacked-out) players to fill it, the *entire* scheduling run failed — every other week too, even ones with no problem at all — reported as a `week_understaffed` conflict with nothing scheduled anywhere. Kyle flagged this as a show-stopper: one bad week shouldn't hold the whole season hostage.

`solveAssignment` now computes each week's actual capacity up front, from blackout data alone (deterministic, not discovered via max-flow failure): `min(playersPerWeek, floor(availableCount / 4) * 4)` — capped to the largest multiple of 4 the available players can fill, since a doubles court needs exactly 4 (never a partial court of 1-3 people; 0 if fewer than 4 are available at all). Weeks that get reduced this way are recorded in `understaffedWeeks` regardless of the overall outcome. The max-flow then runs against these per-week capacities instead of a uniform `playersPerWeek` everywhere, and "feasible" now means *the flow saturates total available capacity*, not necessarily every player's target — see `playerShortfalls` below.

**Deliberately no auto-rebalancing.** This was an explicit choice (Kyle picked "leave it open, fix manually" over an auto-rebalance option that would nudge every player's target down slightly to keep the season's math balanced). So: nobody's `target_games` is touched. Whoever's games got cut by the reduced week just ends up short of their configured target for the season — `playerShortfalls` in the engine's result lists exactly who and by how much (`{playerId, target, achieved, deficit}`), and it's already visible for free on the existing Admin → session → Stats page (played vs. target per player) without any new UI. If the admin wants to make it up, that's a manual call — bump someone's target on a future re-schedule, or fill the gap with a sub.

**What happens in the DB/UI:** `scheduleRun.js` still writes the full schedule for every week (understaffed weeks just get fewer/zero `week_assignments` rows), then flags each understaffed week with `needs_attention = 1` and an explanatory `notes` string (distinct wording for "no match possible" (0 players) vs. "short-staffed" (some players, fewer than normal)) — this reuses the exact same flag/notes mechanism session cards already render with a ⚠. The `POST /sessions/:id/schedule` route's flash message also names the shortfall directly (e.g. "1 week was short-staffed... 2 player(s) are short of their target this run: Alice (2 of 3), Bob (2 of 3).") so it's not a surprise found later. That flash message only shows once, though — the dashboard's per-session flags (`GET /admin`) also include a dedicated `needsAttention` count (weeks where `needs_attention = 1`, upcoming, not locked) with its own wording ("N week(s) need attention — short-staffed or otherwise flagged"), so a genuinely understaffed week stays visible on the dashboard days later, not just in that one-time message. It's deliberately a separate flag from `unfilledBallDuty` — a week with 0 players has no ball duty either, but "missing ball duty" undersells what's actually wrong, so `unfilledBallDuty`'s query explicitly excludes `needs_attention = 1` weeks to avoid double-flagging the same week under a misleading label.

**Filling an understaffed week manually:** the existing "Reassign" button only swaps who's in an *already-existing* assignment row, so it can't fill a week that has zero assignments at all. `POST /sessions/:id/weeks/:weekId/add-player` (new "Add a player…" dropdown on each week card, shown only when the week isn't locked *and* has fewer than `players_per_week` assignments — enforced server-side too, not just by hiding the button) inserts a brand-new `week_assignments` row instead, slotted into the next available court/team position. **Not marked `is_sub`** — that flag specifically means "this person is covering someone else's dropped slot" (`claimSub` in subFlow.js) and drives the "(sub)" label everywhere plus the Stats page's target-vs-played split, which buckets `is_sub` games separately from a player's own target progress. Since this route only ever fires on a week that's genuinely short, whoever gets added is filling their own real slot, not subbing for anyone, so it correctly counts toward their season target like any other scheduled game. It allows picking a player who blacked out that date (an admin override, same pattern as Reassign) — the dropdown labels them `(blackout)` so that's an informed choice, not an accident. If the add brings the week back up to its normal full size, `needs_attention` clears automatically, same as a full regeneration would; if it's still short, the flag stays. Re-running "Schedule these players" wipes and recomputes every open week as usual, so a manual add here doesn't survive a full re-schedule any more than a manual Reassign does.

### Player-target-unreachable: auto-absorbed onto another player, not a hard fail

A different failure mode from understaffed weeks above, easy to conflate but structurally distinct: understaffed weeks are about a *week* not having enough total available players (the week itself gets reduced and flagged, nobody's target changes). This one is about a *specific player's own* blackout dates capping how many weeks they personally could ever play, independent of whether every week they miss is otherwise fully staffed by other people. Reported first (via `solveAssignment`'s post-infeasibility diagnostics) as a `player_target_unreachable` conflict.

Originally this hard-failed the *entire* scheduling run — same show-stopper shape as the old understaffed-weeks bug, just for a different root cause, and reported by a real production case (Kyle, 2026-08-10: a player's target of 14 became unreachable after entering new blackout dates left only 13 available weeks). Unlike understaffed weeks, this one can't be fixed by simply reducing a week's capacity: since every player's target must sum to exactly `weeks × players_per_week` and doubles courts are exact groups of 4, if one player can't hit their number, *someone* has to play one more game than their own configured target to keep every court full — dropping a whole court (4 games) to avoid ever touching another player's target was considered and rejected as disproportionate collateral damage for what's typically a 1-2 game shortfall.

`engine.js`'s `attemptAutoAbsorb()` handles it: when solveAssignment's *only* conflicts are `player_target_unreachable` (never when a deeper `combined_conflict` is also present — see its doc comment for why that case is deliberately left alone), it caps the affected player(s) down to their actual achievable max and hands the *exact* deficit to whichever other player(s) have room, preferring the lowest-target players first (spreads the bump onto whoever's playing least, one game at a time round-robin if the deficit is more than 1), then retries the max-flow with these adjusted numbers. If that retry also fails (no aggregate slack anywhere, or the specific routing still doesn't work out), it gives up and the original conflict is reported as before — this never loops or guesses further.

**This is a narrower exception to "no auto-rebalancing," not a reversal of it.** Kyle explicitly chose this (2026-08-10, see `Full_Scope_Of_Work.md` §14) over both "always hard-fail, admin manually rebalances targets before re-running" and "always drop a whole court instead of ever touching a target." What makes it different from the auto-rebalance option rejected for understaffed weeks: this only ever touches the specific player(s) who structurally can't hit their own number plus whoever explicitly absorbs the exact deficit — never a broad, opaque nudge to everyone's targets — and `session_players.target_games` in the DB is never written to; only this run's actual game counts differ from configured. Every adjustment is reported via `result.targetAdjustments` (`{playerId, configuredTarget, effectiveTarget, reason: 'own_blackout_limit' | 'absorbed_shortfall'}`), named in the `POST /sessions/:id/schedule` flash message (`scheduleRun.js`'s `cappedSummary`/`absorbedSummary`), and visible after the fact via the Stats page's existing target-vs-actual view — same visibility pattern as `playerShortfalls` for understaffed weeks.

**Fixed alongside this:** neither `player_target_unreachable`'s nor `combined_conflict`'s detail string ever actually named the affected player(s) anywhere in the UI — `engine.js` is a pure, DB-free module with no access to names, and nothing downstream resolved `playerId`/`involvedPlayerIds` before rendering `c.detail` verbatim (`session_detail.ejs`, `status.ejs`). `scheduleRun.js`'s `runScheduler()` now enriches conflicts with resolved names (`playerName`/`involvedPlayerNames`, folded into `detail` too so every existing view benefits without changes) before storing to `sessions.schedule_conflicts` — this is the one place with both the raw conflicts and the roster's names in scope together.

### The Status page (`GET /admin/status`, `src/services/statusPage.js`)

A dedicated page, separate from the dashboard, for two things: a flattened to-do list of every "needs a human" item across *all* non-archived sessions (not just per-session counts — actual names/dates), and a read-only preview of what the cron loop is about to do over the next N days, so "is the reminder system actually working" is answerable by looking at a page instead of waiting for match day and hoping.

`getAttentionItems()` returns, across every non-archived session: session-level scheduling conflicts (most urgent — an entire "Schedule these players" run failed, nothing was written), `needs_attention = 1` weeks with their notes, open/escalated/unfilled sub requests, players who've been reminded but haven't confirmed, weeks missing ball duty (excluding `needs_attention` weeks — same reasoning as the dashboard's identical exclusion, see "Understaffed weeks" above), and which sessions have reminders paused. This is the same underlying data as the dashboard's per-session `flags`, just flattened into specifics instead of counts.

`getUpcomingActions(days)` is the more interesting half: it mirrors — does not call — `processReminders()`/`processFollowUps()`/`escalateOverdueRequests()`/`processWeekLocking()`'s own eligibility logic (same email_log dedup checks, same `zonedTimeToUtc`/`addDays` timezone math, same `reminders_enabled`/`archived_at` filters), computing what would happen without sending anything or writing to the DB. Because it duplicates rather than reuses cron.js's internals (those functions have their side effects baked in, not separable from the eligibility checks), **keep this in sync by hand if cron.js's due-date logic ever changes** — `cron.FOLLOW_UP_TIME` is exported specifically so at least that one constant can't drift between the two.

Reminder events are precise — based on real, current `email_log` state, which only moves forward. Follow-up and escalation events are inherently speculative (`speculative: true` on the returned event): a follow-up depends on who's still unconfirmed *by the time it would actually fire*, an escalation on whether the sub request is still open then — both computed "as of right now" and worded as such in the view (`status.ejs`). Week-lock events are deterministic and, along with reminders, carry a real `overdue: true` flag when `at` has already passed but the underlying condition (week still unlocked, recipients still pending) hasn't been resolved — a concrete, useful signal that the cron loop has stalled, not just a stale flash message. One nuance worth remembering if this is ever touched: a follow-up candidate is only included while `now < matchAt` (mirrors `processFollowUps()`'s own `now >= matchAt` skip) — without that check, a week whose match has fully passed without ever being processed would show a misleadingly-not-overdue follow-up entry instead of correctly falling through to just the (overdue) reminder and lock entries, which are the real signal something's stuck.

### Token-based actions: single funnel, hash-only storage, multiple live tokens per assignment

Every player-facing state change (confirm, need-a-sub, claim-a-sub-offer) is gated behind a single-use-per-token link: `crypto.randomBytes(32)` generated in `src/services/tokens.js`, only the SHA-256 *hash* is ever stored — the raw value exists only in the outbound email/redirect. Routes follow GET-renders/POST-mutates throughout `src/routes/public.js`: a GET on `/confirm/:token`, `/need-sub/:token`, `/claim-sub/:token` only looks up and displays state; the actual mutation only happens on the POST from that same page, which is also where the "are you sure?" step lives for `/need-sub`.

`sub_offers.token` is still a single column (one offer = one link, no reason to have more). But confirm/need-sub links for a `week_assignments` row go through `src/services/tokenStore.js`, backed by a separate `week_assignment_tokens` table, **not** a single `week_assignments.token` column (that column still exists in the schema but is vestigial/unused — never dropped, per this app's additive-only migration philosophy). This replaced a real bug: with one token column, minting a new link (e.g. the morning-of follow-up nudge) silently invalidated whatever link had already gone out in an earlier email, so a player who went back to their first reminder instead of the newer follow-up got "Link not found" despite never having clicked anything. Multiple tokens can now be valid for the same assignment at once — `tokenStore.issueToken()` never touches previously issued tokens. A token only stops working when explicitly invalidated via `tokenStore.invalidateTokensForAssignment()` (called when the assignment leaves scheduled/confirmed — `subFlow.createSubRequest()` when status becomes `needs_sub`, `subFlow.claimSub()` on the original assignment when it becomes `subbed_out`, and the admin `reassign` route since the slot now belongs to a different player) or `tokenStore.invalidateTokensForWeek()` (called by `cron.processWeekLocking()` once the week's match time has passed — see below). `tokenStore.findAssignmentByToken()` also independently refuses a token whose week is already `locked`, as a second line of defense in case invalidation hasn't run yet for some reason. When adding a new place that issues or should kill a confirm/need-sub link, go through `tokenStore.js` — don't read/write `week_assignments.token` directly, and don't invent a third invalidation path.

All sub-request creation — whether triggered by an emailed token, the admin's manual resend, or the self-service `/request-sub` page — funnels through the single `subFlow.createSubRequest()` function. `/request-sub/start` does not duplicate that logic; it just mints a fresh token (`tokenStore.issueToken`) for the chosen assignment and redirects into the normal `/need-sub/:token` flow, so there is exactly one code path that fires the fan-out emails. Keep it that way when adding new entry points — don't call the DB mutations directly from a route handler.

### Blackout dates: locked after scheduling, self-service saves directly

Self-service blackout-date submission (`GET/POST /blackout`) writes straight to `blackout_dates` — `POST /blackout` validates the submitted `player_id` is actually enrolled and the submitted dates are real `weeks.match_date` values for that session, then (inside a transaction) deletes that player's existing `source = 'self'` rows and inserts the new selection, redirecting with `?saved=1` for the "Blackout dates saved." notice. Deliberately scoped to `source = 'self'` on the delete so a player's own resubmission can never wipe out a blackout date the admin set for them directly (`source = 'admin'`, via the admin blackout page).

There used to be an email-confirmation step here — submitting staged the dates in a `blackout_pending` table and emailed a confirm link to the player's own address before anything took effect, as an anti-abuse measure against a fabricated `player_id` in the form. Removed by product decision: too much friction for a small trusted group. The tradeoff it gave up: a submission now takes effect immediately for whichever name is selected in the dropdown when the form is submitted, with no independent check that the real player is the one who did it. The one remaining guard is that `sendBlackoutNotice()`'s emailed link (see below) pre-selects the *recipient's own* name via `?player=<id>`, so a player following their own email link can't accidentally pick someone else — but nothing stops them from picking a different name manually on the page. `blackout_pending` and its routes/email template are gone from the code path; the table itself is left in the schema as vestigial (additive-only migration philosophy — never dropped), and `src/views/blackout_confirm.ejs` is now dead/unreferenced.

Blackout dates are only editable by players while a session is `status = 'draft'` — once "Schedule these players" moves it to `scheduled`/`active`, `GET /blackout` disables the checkboxes and hides the Save button, and `POST /blackout` redirects with `locked=1` without writing anything. The admin-side blackout page (`POST /admin/sessions/:id/blackouts`, `source = 'admin'`) is intentionally unaffected by any of this — it writes directly with no lock, since it's the admin's own override tool for after scheduling has happened.

This surfaced a pre-existing structural gap: `weeks` rows are only ever created by `ensureWeeksExist()`, which used to be called exclusively from inside `runScheduler()` — but blackout dates need to be collected *before* the first scheduler run (per the app's own "Add blackout dates, then click Schedule these players" flash message). Both `GET /blackout` (public.js) and `GET /sessions/:id/blackouts` (admin.js) now call `if (session.status === 'draft') ensureWeeksExist(session.id)` before querying weeks, so the checkbox list exists from the moment a draft session is created. Relatedly, `sessionHelper.js`'s `getViewableSessions()` (used by `/schedule`, `/lookahead`, `/calendar`, `/pdf`, `/request-sub`) only ever returns `scheduled`/`active` sessions, which is correct for those pages (nothing to show pre-schedule) but would also hide a `draft` session from the blackout page entirely. `resolveSession(req, { includeDraft: true })` — used only by `GET /blackout` — pulls from `getBlackoutViewableSessions()` instead, which additionally includes `draft`. Don't pass `includeDraft` on any other public route; they have nothing meaningful to render for a session with no schedule yet.

### Notifying the roster that blackout dates are open

Nothing in the app told players blackout dates existed to fill in — the self-service `/blackout` page only worked if a player already knew the URL. `POST /sessions/:id/notify-blackouts` (button on `blackouts.ejs`, only rendered while `session.status === 'draft'`) sends `email.sendBlackoutNotice()` to every currently-enrolled active player, once per click — not automatic on session creation (deliberately: the admin may still be adjusting the roster right after creating a session, so this is a manual, repeatable "ready now" action rather than a one-shot trigger tied to `POST /sessions`). Guarded server-side the same way the player-facing page already is: refuses (with a flash error, no email sent) if the session isn't `draft` anymore, since a scheduled session's `/blackout` page is locked and pointing players at it would be a dead end. Links to `/blackout?session=<id>&player=<recipient's own id>` — `GET /blackout` already reads `?player=` to pre-select a name in the dropdown (was previously only ever set by the page's own `<select onchange="this.form.submit()">`), so each recipient's link lands with their own name already chosen instead of the bare dropdown. This is a convenience, not a security boundary — there's no token, so the query param is guessable/editable. Since `POST /blackout` now saves directly with no confirmation step (see "Blackout dates" above), this pre-fill is actually the only thing standing between a player's own emailed link and someone else's dates getting changed by mistake — following the link and clicking Save can't land on the wrong person, but manually switching the dropdown first still can.

### Blackout visibility on the admin blackout page and session detail page

Two read-only additions, both sourced from `blackout_dates` with one query per page (not per player/week) to avoid N+1s. `GET /sessions/:id/blackouts` now also queries every `blackout_dates` row for the session joined to `players.name`, groups it in JS into `blackoutsByPlayer` (`[{name, dates: [...]}]`, ordered by player name from the `ORDER BY p.name, bd.date` in the query), and `blackouts.ejs` renders it as a table above the existing per-player edit form — this is purely a summary view; editing still only happens through the existing player-select-then-checkboxes form below it. `GET /sessions/:id` (session_detail) separately queries every `blackout_dates` row for the session joined to `players.name`, groups it into a `Map<match_date, [names]>` (`blackedOutByDate`), and stamps each `weekRows` entry with `blackedOutNames` (looked up by `w.match_date`); `session_detail.ejs` renders `Blacked out this week: ...` right under each week's header, before the per-player rows, so it's visible before touching Reassign — this is informational only and doesn't filter or annotate the Reassign dropdown, which still lists the full roster and still allows a blackout override with a flash warning (see the `reassign` route).

### Reminder-sent indicator (admin session detail page)

`week_assignments.status` intentionally does NOT get a "reminder sent" value — email-send history is an orthogonal concern to commitment state and is already tracked in `email_log`. Instead, `GET /admin/sessions/:id` queries `email_log` once per week for rows with `category IN ('reminder', 'followup_reminder')` matching `related_week_id`, builds `remindedEmails`/`followedUpEmails` sets keyed by `to_email`, and stamps each assignment with `a.reminded` / `a.followedUp` booleans. `session_detail.ejs` renders a small `(reminded)` / `(reminded ×2)` tag right after the status badge, but only when `a.status === 'scheduled'` — once a player confirms or needs a sub, the tag is suppressed since it's no longer relevant to what the admin needs to act on.

### "Lock this schedule": a deliberate marker, distinct from the automatic draft -> scheduled flip

Kyle, 2026-08-13: the first "Schedule these players" click already moves a session's `status` out of `draft`, but that's an automatic, one-way side effect of the *first* click — not a deliberate signal that the admin is done adjusting things. Between that first click and whenever the admin actually considers the schedule final, real drift can still happen: the roster can still be edited, an admin can still add/change blackout dates directly (the self-service `/blackout` page locks once `status` leaves `draft`, but the admin-side blackout page is intentionally unaffected by that lock — see "Blackout dates" above), and another session's roster changing can shift the double-booking picture out from under this one. "A schedule technically exists" and "this is the version we're standing behind" are genuinely different moments, and this grew out of a specific need: a planned deferred sub-needed notification (still under discussion, not yet built as of this writing) that should wait for the *second* moment, not the first.

`sessions.schedule_locked_at` (nullable `TEXT` timestamp, `ensureColumn`-backfilled to `NULL` for every existing row) is set/cleared only by the admin, via a "Lock this schedule" / "Unlock schedule" button on `session_detail.ejs` (`POST /admin/sessions/:id/lock-schedule` / `.../unlock-schedule`), right next to Archive — same manual, deliberate, admin-judgment-call pattern as everything else in this app. **Locking does not restrict any further edits** — the roster form, re-running "Schedule these players," and blackout dates all work exactly the same before and after. It's purely a marker (shown as a `schedule locked` badge in the header, plus the exact timestamp in the metadata line underneath) and, going forward, a gate for behavior that should wait for a stable, communicated schedule rather than fire the moment scheduling first happens. Logged via `logActivity()` (`session.lock_schedule` / `session.unlock_schedule`) like every other admin action.

Ad-hoc sessions have no equivalent moment to lock — there's no season-long schedule generated for them, just a rolling per-week invite/sign-up/finalize cycle (see "Ad-hoc sessions" below) — so the route refuses with a flash error for `session_type = 'adhoc'` (defense in depth; the button itself is simply never rendered on `admin/adhoc_session_detail.ejs`, which doesn't share `session_detail.ejs`'s template at all).

Verified live: the badge and button correctly toggle between locked/unlocked states across a real lock -> unlock round trip via the actual routes, the timestamp renders in the metadata line once locked, and a direct POST to lock an ad-hoc session's schedule is refused with `schedule_locked_at` left `NULL`.

### Archiving a session

`sessions.archived_at` (nullable timestamp, `ensureColumn`-backfilled) is a separate concern from `status`: it's a visibility toggle, not a lifecycle stage. `POST /sessions/:id/archive` / `.../unarchive` (buttons on `session_detail.ejs`'s top actions row, and inline on each row of the dashboard's "Archived sessions" section) just set/clear that column — status is untouched either way. Archiving does **not** delete anything (unlike `POST /sessions/:id/delete`, see below) and doesn't change what status-driven logic does with the session (a scheduled-and-archived session still locks its weeks, for instance) — it only changes what's *visible*:

- `GET /admin` (dashboard) — the main flags list filters `archived_at IS NULL`; archived sessions move to a separate muted section at the bottom instead of disappearing outright, so they're still reachable to view stats/history or unarchive.
- `sessionHelper.js`'s `getViewableSessions()`/`getBlackoutViewableSessions()` — both add `archived_at IS NULL`, so an archived session vanishes from every public page's session picker and from `resolveSession()`'s fallback, exactly like it was never scheduled.
- `cron.js`'s `processReminders()`/`processFollowUps()` and `subFlow.js`'s `escalateOverdueRequests()` all additionally filter `archived_at IS NULL` on their session queries — archiving is meant to go fully quiet (no more emails), not just hide from the dashboard, in case someone archives a session that still has open weeks or an unresolved sub request. `processWeekLocking()` and `flagStillUnfilled()` deliberately do *not* filter — both are silent bookkeeping (no email, no dashboard flag), so there's no reason to skip them, and it keeps a session in a consistent state if it's ever unarchived later.

Direct URLs to an archived session (`GET /sessions/:id`, `/edit`, `/stats`, `/blackouts`) still work normally — archiving only removes it from *listings*, not access. `session_detail.ejs` shows an `archived` badge next to the status badge as a reminder when you're looking at one directly.

### Overlapping-session double-booking guard

Multiple concurrent sessions are supported by design (see `sessionHelper.js`'s "overlapping/concurrent sessions are allowed" comment) — the same install can run a first-half and second-half session, or two different clubs, at once. That design left a real gap, flagged as an open question in `Full_Scope_Of_Work.md` §14 and never answered until the code was actually checked: `runScheduler()`/`ensureWeeksExist()` in `scheduleRun.js` operate entirely within one `session_id` — roster, blackout dates, and week generation never look at a player's assignments in any *other* session — so nothing stopped the same player being enrolled in two sessions whose matches actually collide.

`sessionHelper.js`'s `findOverlappingSessionEnrollments(sessionId = null)` closes that gap as a warning, not a hard block — matching the app's existing pattern for judgment-call conflicts (the blackout-override warning, understaffed-week flagging) rather than refusing to save. The trigger condition is deliberately narrow and cheap to reason about: two non-archived sessions with the *same* `match_day_of_week` and *overlapping* `start_date`/`end_date` ranges, sharing at least one active enrolled player. `match_time` is intentionally **not** part of the trigger — there's no match-duration field to compare against, so two sessions on the same day with different hours would still flag, and the admin is expected to judge from the displayed times whether it's a real conflict or two different time slots that happen to share a weekday. Pass a `sessionId` to scope to conflicts involving one specific session (used right after saving a roster); call with no argument to check every non-archived session against every other, once, for the flattened Status page view — calling it per-session there would double-count each pair.

Surfaced in three places, mirroring how other "needs a human" conditions are surfaced elsewhere in the app:
- **Flash message** on `POST /sessions` and `POST /sessions/:id` (admin.js's `overlapWarningText()`) — fires immediately after saving a roster if the just-saved session now conflicts with another.
- **Session detail page** (`GET /sessions/:id`) — a persistent "Overlapping session enrollment" card, so it doesn't just flash once and vanish; the other session's date range and match time are shown right in the message.
- **Dashboard flags and the Status page** (`statusPage.js`'s `getAttentionItems().overlappingEnrollments`) — same treatment as `needsAttention`/`unfilledSubs`, so a conflict introduced by editing the *other* session's dates (not the one you're currently looking at) still surfaces without having to revisit every session's edit page.

Not wired into `scheduleRun.js` itself — this is enrollment-level (who's in which session), not schedule-level (which week they're actually assigned to), and deliberately stays a soft warning rather than blocking "Schedule these players", consistent with this app's general philosophy of flagging conflicts for the admin rather than silently refusing to schedule.

### `session_players.original_target`: preserves the season-long number, `target_games` doesn't

`target_games` is a single mutable field — the roster-save route overwrites it every time the admin resubmits `session_form.ejs`'s roster table, and nothing in the scheduler, cron, or week-locking ever adjusts it automatically as games actually get played (the "(remaining)" wording in that column's header is purely instructional: if a mid-season roster edit forces a resubmit, the admin is expected to manually recompute the number down to just the open weeks left, using the "Already played" column as a reference — see "The scheduling engine is pure and separate from the DB" above). Kyle, 2026-08-13: that meant the *original* full-season number had no history anywhere — the Stats page read the exact same `target_games` column, so overwriting it mid-season silently lost the original figure with nothing keeping a record.

`original_target` (nullable `INTEGER`, added via `ensureColumn`) is snapshotted once, in `admin.js`'s `saveRoster()`, only in the branch that `INSERT`s a brand-new `session_players` row (first-ever enrollment) — the `UPDATE` branch used for every subsequent edit deliberately never touches it. Existing rows predate the column and have no way to recover their true original number, so `db/index.js` backfills `original_target = target_games` for any row where it's still `NULL` — run unconditionally on every boot rather than gated behind a one-time flag, since after the first boot no row should ever match that `WHERE` clause again (new enrollments always set it at `INSERT` time). The Stats page's "Target" column now shows `original_target` in parentheses next to the current `target_games` only when they differ, the same "only show the aside when it's not redundant" pattern already used for the Played column's `(target N)` note.

Verified live: a pre-migration row (simulated with `original_target` left `NULL`, mirroring an old install) gets backfilled to match its `target_games` on the next boot; a brand-new enrollment sets both columns to the same value at `INSERT` time; a simulated mid-season edit that lowers `target_games` leaves `original_target` untouched; and the real Stats page route renders "(originally N)" only for the row where they diverge, with no note at all for an unchanged player.

### `session_players.priority`: advisory only, deliberately not enforced by the scheduler

The overlap guard above only ever warned — nothing stops the *scheduler* from actually assigning the same player to play in two colliding sessions on the same calendar date, since `runScheduler()` operates entirely within one `session_id` with no visibility into any other session's schedule. Reported by Kyle (2026-08-11) as a real gap once he had two overlapping sessions sharing a roster.

This briefly had a real fix — `scheduleRun.js`'s `crossSessionPriorityExclusions(session, roster)`, added and reverted the same day (2026-08-11) — that made `session_players.priority` (nullable `INTEGER`, added via `ensureColumn`; still present in the schema, kept per this app's additive-only migration philosophy) actually exclude the lower-priority session's player from every calendar date the two sessions shared, the same way a real blackout date would. It was reverted after a real case Kyle hit directly: reserving *every* shared date for the winning session (not just the ones it turned out to need) could leave the losing session's player with zero available dates at all, and when the resulting deficit was too large for `attemptAutoAbsorb()` (see "Player-target-unreachable" above) to redistribute onto other players, the *entire losing session's* scheduling run aborted and wrote nothing — for every player in that session, not just the one actually in conflict. That's a disproportionate blast radius for what's fundamentally a one-player, one-date scheduling nuance, and it directly contradicted this app's standing "warn, don't block" philosophy for exactly this kind of judgment call.

**Current, permanent behavior: priority is a note, not a rule.** `session_players.priority` is still set on the roster table of `session_form.ejs`, right next to Target games — lower number is *meant* to indicate the session that should probably win a shared player if it comes to that, and a hint ("also in Session B — set priority here and there") still appears under any player flagged by `findOverlappingSessionEnrollments()`. But nothing in `scheduleRun.js` reads it. `runScheduler()`'s `isBlackedOut` check only ever consults real `blackout_dates` rows (plus, as of 2026-08-12, carryover from another session's real blackout dates — see "Blackout date carryover" below, a deliberately different and much narrower mechanism than the one reverted here) — there is no priority-driven cross-session exclusion set built or merged in. `findOverlappingSessionEnrollments()`'s `resolution` field (`'unresolved' | 'tied' | 'a_wins' | 'b_wins'`) is purely descriptive now: it tells the admin which session priority *suggests* should win, for whoever ends up fixing a real conflict by hand, but doesn't mean the conflict was actually prevented. Every UI surface that shows this (session detail's "Overlapping session enrollment" card, the dashboard flag, the Status page) was updated to drop "wins/excluded" language in favor of "flagged as higher priority" / "no priority set" / "priority tied" — and the dashboard/status counts now include every overlapping pair regardless of resolution, since none of them are actually "handled" anymore.

Two sessions sharing a player on the same date are now *always* possible and *always* just a warning up front (at enrollment time, via the overlap guard) — the only thing that changed after the revert is what happens once scheduling actually runs: nothing auto-excludes anyone, so a real double-booking can and will occur if the two sessions' generated schedules happen to collide. See the next section for how that's now made visible to the player themselves, not just the admin.

### Blackout date carryover across sessions

Kyle, 2026-08-12: entering the same blackout date twice for a player enrolled in two same-day-of-week sessions was pure busywork — "If I enter in a blackout date for Kyle for session 1 on a Wed, I shouldn't need to enter in that blackout date again for Kyle on session 2, which is also on a Wed." `sessionHelper.js`'s `carriedOverBlackoutsForSession(sessionId)` closes that gap: for a given session, it finds every `(player, date)` where that player already has a real `blackout_dates` row in some *other* non-archived, `session_type = 'regular'` session, and that date happens to also be one of this session's own `weeks.match_date` values for a player currently on this session's roster. Live-computed and never stored (same pattern as `doubleBookingMapForSession()`) — if the source blackout is later removed, the carryover disappears on the very next read with nothing to clean up, and there's no write-fanout to get out of sync.

**This is deliberately not a repeat of the reverted `session_players.priority` auto-exclusion above, despite touching the same `isBlackedOut` check.** The reverted feature failed because it reserved *every* calendar date two sessions happened to share, whether or not the player actually needed it off — a blanket policy that could manufacture a large, artificial deficit with no real-world basis and take down an entire session's scheduling run. Carryover only ever includes dates someone *deliberately entered as a real blackout* somewhere — inherently a small, sparse set of genuine "this player truly cannot play this date" facts, exactly the kind of thing `blackout_dates` already existed to hold. Because it's folded straight into the same `blackoutSet` a normal blackout row builds (`scheduleRun.js`), a carried-over date gets the exact same graceful degradation as any other blackout — `week_understaffed` reduction, `attemptAutoAbsorb()`, `playerShortfalls` reporting — with zero new code in the engine and zero new failure mode to worry about.

**Where it shows up.** Both blackout pages (`GET /admin/sessions/:id/blackouts` and the public `GET /blackout`) compute the same `carriedOverMap` and use it two ways: a summary list ("Carried over from other sessions" / already covered under "All blackout dates, by player" on the admin side) so it's visible without hunting, and — more importantly — the per-player edit checklist renders a carried-over date as a `checked disabled` checkbox with a note naming the source session, rather than a normal editable one. This is deliberate, not just cosmetic: a disabled checkbox never submits, so the existing DELETE-then-INSERT save logic on both `POST` routes is completely unaffected by carryover — no risk of accidentally writing a redundant real row into the second session, and no risk of a carried-over date silently disappearing if the admin resubmits the form without touching it. Editing a carried-over date can only happen at its actual source session, by design — a blackout date describes a real day a player can't be anywhere, so there's exactly one true value for it regardless of which session's page you're looking at it from.

**Scope.** Regular sessions only, in both directions (source and target) — ad-hoc sessions have no blackout concept at all (see "Ad-hoc sessions" below), so `carriedOverBlackoutsForSession()` filters to `session_type = 'regular'` on the source side, and is simply never called for an ad-hoc session's own (nonexistent) blackout page. No day-of-week filtering is needed or done — the join is against the target session's actual `weeks.match_date` values, so it naturally only ever matches a real match day in both sessions, whatever their respective day-of-week configuration happens to be.

### Pausing automatic reminders (`sessions.reminders_enabled`)

A per-session toggle (checkbox on `session_form.ejs`, default checked/1) for pausing the automatic reminder + follow-up cron pass — added for testing a session without spamming real players while still being able to trigger sends deliberately. `cron.js`'s `processReminders()`/`processFollowUps()` both add `reminders_enabled = 1` to their session query, same spot as the `archived_at IS NULL` filter above. Deliberately does **not** gate `sendRemindersNowForWeek()` (the admin's "Send reminders now" per-week button) or the per-player "Resend link" route — both are explicit admin actions, not automatic sends, so they always work regardless of the toggle; that's the whole point of the feature; pause the automatic pass, keep manual control. `processEscalations()`/`processWeekLocking()` are untouched too — sub-request escalation and week-locking aren't "reminders" and have their own reasons to keep running (see "Archiving" above). Shown as a badge on `session_detail.ejs`'s header and a dashboard flag ("Automatic reminders are off for this session") when off, specifically so it's hard to forget a session was left in test mode.

This surfaced (and fixed) a real, previously-silent bug: a blank or malformed `match_time`/`reminder_time` doesn't just fail to parse in `tz.js`'s `zonedTimeToUtc()` — it produces an `Invalid Date`, and `Invalid Date` compares as neither `<` nor `>=` any real date. Every cron "is this due yet?" check is a `<`/`>=` comparison against `now`, so depending which one, a bad time value silently flipped the answer to the *wrong* one instead of erroring: an empty `reminder_time` made `processReminders()` treat the reminder as permanently overdue (would have spammed on every tick), while an empty `match_time` would have made `processWeekLocking()` lock every week immediately. Three layers now guard against this: `admin.js`'s `invalidTimeFields()` rejects a blank/malformed `match_time` or `reminder_time` server-side on session create/update (`TIME_RE`, strict `HH:MM` 24h) before it ever reaches the DB; `zonedTimeToUtc()` itself now throws instead of silently producing `Invalid Date`, as a second line of defense for anything that reaches it some other way (a pre-existing row from before this fix, a direct DB edit); and `processReminders()`/`processFollowUps()`/`processWeekLocking()` each wrap their per-session loop body in try/catch, logging and moving on to the next session, so one bad row can't take down every other session's reminders for that tick. Also fixed in passing: `session_form.ejs` never received or rendered `flashMsg` at all (the route didn't pass it, and the template didn't forward it to `admin_header`) — meaning every validation error on this page, including the pre-existing `invalidPlayersPerWeek` one, was silently swallowed since the day it was added. Both `GET /sessions/new` and `GET /sessions/:id/edit` now pass `flashMsg: popFlash(req)`, and the template forwards it.

### Blank-field validation on FK-referencing forms (`ball-duty`, `reassign`, players, sub list, session dates)

A second landmine class, distinct from but sibling to the `Invalid Date` one above: `Number('')` evaluates to `0` in JavaScript, not `NaN`. Several routes took a form field straight from `req.body`, ran it through `Number(...)`, and used the result as a foreign key — `week_assignments.player_id`, `weeks.ball_duty_player_id` — with no check that a player with that id actually exists. A blank `<select>` submits `''`, which becomes `0`, which is numerically valid but not a real player id (ids start at 1 via `AUTOINCREMENT`), so it sailed past every existing check and only failed once it hit `PRAGMA foreign_keys = ON`, surfacing as a raw, unstyled "FOREIGN KEY constraint failed" 500 page instead of a normal flash message. `POST /sessions/:id/weeks/:weekId/ball-duty` and `POST /sessions/:id/weeks/:weekId/reassign` now both look up the submitted player id first and flash a plain "Pick a player..." error if it doesn't resolve to a real row, before ever reaching the `UPDATE`.

Separately, `POST /players`, `POST /players/:id/edit`, and `POST /sub-list` had no presence/format validation at all — unlike `POST /admins`, which was already the correct reference pattern (`if (!name || password.length < 8) { flash(...); return res.redirect(...); }`). A blank name/email silently "succeeded" (302 redirect) and created a real row with empty strings, no error anywhere. All three now share `invalidPlayerFields(b)` in `admin.js` (non-blank name, `EMAIL_RE`-matched email) and reject before the `INSERT`/`UPDATE`.

Session dates had the same gap from the other direction: a blank `start_date`/`end_date` isn't caught by SQLite (they're plain `TEXT` columns) and doesn't throw in `scheduleRun.js`'s `datesForDayOfWeek()` either — it builds a JS `Date` from the empty string, gets `Invalid Date`, and the function's `while (cur <= end)` loop (same `Invalid Date`-comparison quirk as above) just never executes, so the session saves fine but silently gets zero weeks with no error telling the admin the schedule is empty. `invalidSessionDates(b)` in `admin.js` now rejects a blank/malformed `start_date` or `end_date` (`DATE_RE`, strict `YYYY-MM-DD`), rejects `end_date < start_date`, and rejects an out-of-range `match_day_of_week`, on both session create and edit, before the row is ever saved.

As defense-in-depth for data that predates these checks (a legacy row, a direct DB edit), `tz.js`'s `addDays()` now throws on non-finite date components the same way `zonedTimeToUtc()` already did, and `ics.js`'s `buildPlayerICS()` now guards `session.match_time` and each `match_date` before building calendar events — a bad `match_time` returns a clean `{ error }` (already handled by the `/calendar/download` route as a 400), and a bad individual `match_date` is skipped rather than corrupting the whole `.ics` file.

### Deleting a session

`POST /admin/sessions/:id/delete` (danger-zone card on the Edit session page) permanently removes one session's data. `players` is a global table — a player row isn't owned by any session, `session_players` is just the join table — so deleting a session never removes a player, even one who's *only* enrolled in that session; they simply stop showing up anywhere until re-enrolled elsewhere. Most session-scoped tables clean up via `ON DELETE CASCADE` on `session_id`/`week_id`/etc. (`session_players`, `blackout_dates`, `blackout_pending`, `weeks` → `week_assignments` → `week_assignment_tokens`, and each week's `sub_requests` → `sub_offers`). `email_log.related_week_id` is the one exception — it deliberately has no cascade, since a sent-email record should outlive a deleted session for support purposes ("did that reminder actually go out?") — so the route nulls `related_week_id` for that session's weeks *before* deleting, otherwise the FK constraint (`PRAGMA foreign_keys = ON`) blocks the cascade with a "FOREIGN KEY constraint failed" error. The confirmation is a plain `onsubmit="return confirm(...)"` (same pattern as backup deletion in `backup.ejs`) with a static message — not one interpolating the session name — since EJS's default HTML-escaping of an apostrophe (`&#39;`) still decodes back to a literal `'` before the browser hands an inline event handler's source to the JS engine, which would break out of the string.

### Full data reset (`src/scripts/reset-data.js`)

`npm run reset-data -- --confirm` clears every player, session, and everything session-owned, for wiping test/dummy data (e.g. from `seed-example.js`) before going live — but deliberately leaves `admins` and `app_settings` untouched so it can never lock the admin out or reset the timezone. Runs `createBackup()` first unconditionally. Deletion order matters here for the same reason as session deletion above, but doubled up: `email_log.related_week_id` has no cascade (so `email_log` is cleared before `sessions`), and `sub_offers.candidate_player_id`/`broader_list_id` *also* have no cascade — so `players` and `broader_sub_list` are only deleted after `sessions` (whose cascade already took every `sub_offers` row with it via `weeks → week_assignments → sub_requests → sub_offers`). Deleting `players` or `broader_sub_list` first would hit a "FOREIGN KEY constraint failed" the moment a still-`pending`/`closed` `sub_offers` row referenced one. With no `--confirm` flag it only prints what it would do and exits — never touches the DB.

### Sub-request state machine

`week_assignments.status` moves `scheduled → confirmed` or `scheduled → needs_sub → subbed_out` (with a new `week_assignments` row created for the incoming sub, `is_sub = 1`). `sub_requests.status` moves `open → filled` (first click wins, in `claimSub()`), `open → escalated → unfilled` via the cron-driven `escalateOverdueRequests()` / `flagStillUnfilled()` in `src/services/subFlow.js`, or `open|escalated|unfilled → resolved_manually` when an admin resolves the slot directly (see below). Only one *open or escalated* sub_request is allowed per week at a time (`hasActiveConcurrentSubRequest`) — a second player needing a sub in the same week is deliberately routed to the admin instead of auto-handled (see the resolved open item in `Full_Scope_Of_Work.md` §10).

**Admin resolving a slot that has an active sub request:** if an admin uses Reassign, or Mark confirmed, on an assignment that currently has an `open`/`escalated`/`unfilled` `sub_requests` row (e.g. reassigning P1's slot after P1 asked for a sub, or the player told the admin directly they can make it after all), that action satisfies the sub request. Both routes (`POST /sessions/:id/weeks/:weekId/reassign` and `POST .../mark-confirmed/:assignmentId` in `admin.js`) call `subFlow.closeActiveSubRequestForAssignment(assignmentId)`, which sets the request's status to `resolved_manually` and closes every still-`pending` `sub_offers` row under it. This matters for two reasons, not just cosmetics: without it, the "sub open" badge on the session detail page and dashboard never clears (it's driven by `sub_requests.status IN ('open','escalated','unfilled')`), and — more seriously — the sub-invite email links already out to other players stay claimable. `claimSub()` only refuses a claim once the request is no longer pending (`status === 'filled'` or, now, `'resolved_manually'`) or the specific offer is no longer `'pending'`; left untouched, a player clicking their still-live invite link after the admin's manual fix would silently flip the admin-reassigned/confirmed row to `subbed_out` and insert an unwanted extra `week_assignments` row for that week. `resolved_manually` is kept distinct from `filled` (rather than reusing it) so `stats.ejs`'s sub history can still tell a self-serve claim apart from an admin intervention — it's just mapped to the same green "confirmed"-style badge there.

### Self-service Request a Sub: email-gated (bot protection) and blackout-aware fanout

Kyle, 2026-08-18, reviewing the self-service flow end to end: `/request-sub` has no login — a player just picks their name from a dropdown — so nothing stopped a script from mashing "Need a sub for this week" for every name in the list. Before this, `POST /request-sub/start` minted a token and redirected the *browser* straight to `/need-sub/:token`'s "Are you sure?" page, which a script could then also submit — a bot never had to prove it was a real person with access to that player's inbox at any point. "I feel like bots could easily send out many emails by pressing that sub button. I want there to be some validation by the player."

**The fix reuses the existing token infrastructure rather than inventing a new one.** `POST /request-sub/start` still mints a token via `tokenStore.issueToken()` exactly as before, but instead of redirecting the browser to the confirm page, it now emails that link to the assignment's own player (`email.js`'s new `sendSubRequestVerification()`) and renders a plain "Check your email" page. The link in that email points at the *same* `/need-sub/:token` GET/POST landing page already used by the automatic reminder's "need a sub" link — same "Are you sure? This will immediately email the other players..." copy, same POST-mutates convention — so no new confirm page or mutation logic was needed; only whoever actually controls that inbox can get past it. This also quietly closes the pre-existing "wrong name picked from the dropdown" risk: since nothing in the DB changes until the *recipient* of this new email clicks through, a mis-click on `/request-sub` is now harmless by construction, not just caught after the fact (the existing `sendSubRequestOwnConfirmation()`, sent right after the real fanout goes out, remains as a second, after-the-fact safety net/audit trail — the two serve different moments, not redundant).

Only `/request-sub/start` changed — the emailed reminder's own "need a sub" link was already gated behind an email a player didn't generate themselves, so it never had this gap. My Page's "Need a sub" button also posts to `/request-sub/start`, so it automatically inherits the same protection (it's equally unauthenticated).

**Candidate fanout now checks blackout dates.** `subFlow.js`'s `fanOutSubRequest()` — the shared candidate computation used by both the immediate self-service/reminder-link path and the deferred admin-flagged path (`fanOutPendingAdminFlagsForWeek()`) — previously only excluded players already playing that week; it never consulted `blackout_dates` at all, so someone who'd explicitly marked themselves unavailable for that exact date could still get a "sub needed" email for it. It now builds a `blackoutSet` the same way `scheduleRun.js`'s `isBlackedOut` does for the scheduler itself — this session's own `blackout_dates` rows, plus anything carried over from another session's real blackout on the same calendar date via `sessionHelper.js`'s `carriedOverBlackoutsForSession()` — and filters candidates against it before creating `sub_offers` or sending anything. Kyle: "The system should check blackout dates and if someone is blacked out for that date, don't send them an email." This is a filter on *unsolicited* candidate emails only, not a hard block — an admin can still manually add a blacked-out player to a week via the existing "Add a player…" override, same as everywhere else in this app that treats blackout dates as a strong signal rather than an absolute rule.

**`/request-sub` now shows the real status instead of the row disappearing.** The page's query previously filtered to `wa.status IN ('scheduled', 'confirmed')` only, so the instant a request went out (or got filled), that week's row just vanished from the list with no feedback that anything had happened. Kyle: "the status on the request a sub page should change reflecting the player already requested a sub for that week" and "once that sub request is filled, the status for that week for that player should be changed to 'subbed out'" — both of these were already true in the database (`createSubRequest()` already sets `needs_sub`, `claimSub()` already sets `subbed_out`); the gap was purely that this page filtered those statuses out before they could be displayed. The query now includes `needs_sub`/`subbed_out` too, `request_sub.ejs` renders the real badge for every status (with the same double-booked-only-while-scheduled/confirmed priority rule used on `/schedule`/`/lookahead`/`/me` — see "Bug found by Kyle, 2026-08-18" above), and the "Need a sub for this week" button is only rendered for `scheduled`/`confirmed` rows — a `needs_sub` row shows "Already requested — waiting for someone to claim it," a `subbed_out` row shows "A sub has taken this spot," neither with a button, since re-requesting either doesn't make sense (and the backend's `hasActiveConcurrentSubRequest` guard would refuse it anyway).

Verified live end-to-end against a seeded scenario (5-player session, one candidate blacked out on the match date): clicking "Need a sub for this week" sent exactly one `sub_request_verification` email to the requesting player and changed nothing in the database; minting and visiting that same token's `/need-sub/:token` link (simulating the email click) showed the existing "Are you sure?" page, and only the POST from there flipped the assignment to `needs_sub` and fanned out `sub_request` emails to the two available non-playing candidates — the blacked-out candidate got nothing; `/request-sub` correctly showed "needs sub" with no button in between; simulating a claim via `/claim-sub/:token` flipped the original assignment to `subbed_out`, and `/request-sub` then correctly showed "subbed out" with no button.

There's also a direct **Clear sub request** button next to the "sub open" badge on the session detail page (`POST /sessions/:id/weeks/:weekId/clear-sub-request`), for the "undo" case — the request itself was a mistake, or got called off — as opposed to Reassign/Mark confirmed, which resolve an active sub request as a side effect of deciding on some *other* outcome (a different player, or an explicit confirmation). It calls the same `closeActiveSubRequestForAssignment`, just triggered directly. Since only one open/escalated/unfilled `sub_requests` row can exist per week at a time (`hasActiveConcurrentSubRequest`), the route only needs `weekId` to find it — no assignment ID in the form.

**Resets status to `scheduled`, not just the week-level flag (Kyle, 2026-08-25).** Originally this only closed the `sub_requests` row and deliberately left `week_assignments.status` at `needs_sub`, on the theory that the admin might not want to assert anything about who's actually playing. Kyle walked through the actual case that comes up: a player picks the wrong week on Request a Sub, or requests a sub and then finds out they can play after all, and asks the admin to put things back — at that point leaving them stuck on `needs_sub` was a real functional gap, not just a cosmetic one, since a `needs_sub` assignment is excluded from the normal reminder/follow-up cron pass, so that player would silently stop getting reminded to play a week they're actually still down for. The route now also runs `UPDATE week_assignments SET status = 'scheduled' WHERE id = ? AND status = 'needs_sub'` right after closing the request (the `status = 'needs_sub'` guard is defensive — it can never clobber a status something else set in the meantime, since it only fires if the row is still sitting exactly where a sub request left it). This assumes the *original* player is the one playing again — if someone else actually stepped in outside the app and the admin needs to record a different player for that slot, Reassign is still the right tool (it resolves the request by recording who's really playing, rather than reverting to the original player), not this button. Their old confirm/need-sub tokens stay dead (invalidated when the sub request was first opened) rather than being reissued here — the next automatic reminder or follow-up will mint fresh ones the normal way; an admin who wants a live link immediately still has the separate **Resend link** button for that.

### Admin-flagged sub requests: rare, silent at flag time, deferred fan-out

A design conversation with Kyle, 2026-08-13, that landed somewhere different from where it started. The original ask was for the admin to be able to reassign a double-booked (or any) player straight to "needs a sub," with the resulting emails held back until a stable moment. Talked through several versions of "what stable moment" — tying it to the "lock this schedule" marker above was considered and dropped ("the 'season is locked' has really nothing to do with it except a visual indicator to the admin... please don't make any more changes") in favor of the much simpler original framing: hold the fan-out until that specific week's own normal reminder time. Also landed on a narrower philosophy for when this should be used at all: **"admins should really not be touching the player schedule except for edge cases. The players should have all the tools to request subs and perform player to player swaps."** The normal path for "I'm double-booked" or "I can't make it" is the player using Request a Sub / Swap a Week (both already fully self-service, and a double-booked player already sees it flagged directly on their own pages — see "Player-facing double-booking visibility" above) — this is the fallback for when the admin needs to force the issue directly, not a replacement for that.

**What it is:** a new option, "— Needs a sub —", in the Reassign dropdown on `session_detail.ejs` (`POST /sessions/:id/weeks/:weekId/reassign`, branched at the very top of the route before any of the normal reassign-to-a-specific-player logic runs). Picking it calls `subFlow.adminFlagNeedsSub(weekAssignmentId)` instead of reassigning to a chosen player: the same `week_assignments.status = 'needs_sub'` transition, token invalidation, and ball-duty-reassignment-needed handling the player-initiated `createSubRequest()` does, opening a `sub_requests` row with `status = 'open'`. The one deliberate difference: **it sends no email of any kind at flag time** — not to the candidate pool, and not even a "you've been marked as needing a sub" notice to the affected player. Per Kyle: "no email confirmation to player. Admin has final say." The player will simply see their own status flip to `needs_sub` if they check their own schedule — same as it would if they'd requested it themselves, just without a notification prompting them to look.

**Why nothing fires immediately, and why it's not the schedule lock:** refused as a separate blast-radius risk to keep small, this is scoped as narrowly as possible — a manual, single-slot flag, not a policy that reaches into other sessions or touches anyone else's numbers, the same "small and deliberate, not blanket" shape as every other cross-cutting feature in this app (blackout carryover, the reverted priority auto-exclusion). `sessions.schedule_locked_at` was considered as the gate and explicitly ruled out — it's unrelated to this feature, purely a marker for "please don't make any more changes to this schedule, it'll make the players angry," with no bearing on sub-request timing.

**The deferred fan-out mechanism:** `sub_requests` gained two columns — `initiated_by` (`'player'` | `'admin'`) and `fanout_sent_at` (nullable `TEXT` timestamp). A player-initiated request still fans out immediately, same as always; an admin-flagged one leaves `fanout_sent_at` `NULL` until `cron.js`'s `processReminders()` reaches that specific week's own normal reminder threshold (the exact same `reminder_days_before`/`reminder_time` check that fires everyone's confirmation reminders) — at that point it calls the new `subFlow.fanOutPendingAdminFlagsForWeek(weekId)`, which finds any `open`/`admin`-initiated/`fanout_sent_at IS NULL` request for that week and sends it. The candidate computation and fan-out email (`sendSubRequestFanout`) were refactored out of `createSubRequest()` into a shared `fanOutSubRequest(subRequestId, requestingPlayerName)` so both the immediate (player) and deferred (admin) paths use identical logic — critically, candidates are computed **fresh at send time**, not snapshotted when the admin flagged it, since the roster of who's already playing that week could genuinely have changed in the intervening days. `fanout_sent_at` being set is what makes this idempotent on every subsequent cron tick — the query only ever finds a request once. Once fanned out, the existing 24-hours-before-match escalation (`escalateOverdueRequests()`) picks it up exactly as it would any other open request — no changes needed there, since it already treats every open request the same regardless of how it was created.

**Backward compatibility:** existing `sub_requests` rows predate both columns and, by definition, could only ever have come from the player-initiated path (this feature didn't exist yet) — `initiated_by` defaults to `'player'` via the column's `NOT NULL DEFAULT`, and `db/index.js` backfills `fanout_sent_at = created_at` for any row still `NULL`, since a pre-existing player-initiated request's fan-out really did go out the moment it was created.

Verified live: flagging a scheduled assignment correctly flips its status, opens a request with zero `sub_offers` and zero `email_log` rows; the flagged slot immediately disappears from `/request-sub`'s picker (existing `status IN ('scheduled','confirmed')` filter, unchanged); a second flag attempt on the same week is correctly refused by the existing concurrent-request guard; `processReminders()` run before that week's reminder threshold does nothing, and run after it correctly fans out to the actual non-playing roster (verified: players still `scheduled` that week get their normal confirmation reminder and nothing else; the flagged player gets no email; only the genuinely non-playing candidates get the sub-request email) and is idempotent on a second call; and the backward-compat backfill correctly fills in both columns for a simulated pre-migration row on next boot.

**Bug found by Kyle, 2026-08-18: a double-booked player flagged "needs a sub" still showed "double booked" everywhere on the public site.** Kyle's exact repro: player is double-booked (correctly shown on `/schedule`), admin picks "— Needs a sub —" from that player's Reassign dropdown (correctly shows "sub open — `<name>`" at the week level on the admin page), but the player's own row on the public schedule kept showing "double booked" instead of reflecting the new `needs_sub` status — the other three players in that week correctly showed "scheduled". Root cause: the double-booked badge logic in `schedule.ejs`, `lookahead.ejs`, `me.ejs`, and `admin/session_detail.ejs` (all four built during the earlier "Player-facing double-booking visibility" pass, before this admin-flagging feature existed) unconditionally rendered the `double_booked` badge and suppressed the real `<%= a.status %>` badge whenever `a.doubleBooked` was truthy — with no consideration for whether status had since moved on.

First fix attempt scoped the override to only apply while `a.status` was `scheduled`/`confirmed`, so `needs_sub` would show through — but Kyle then asked (same day) for the opposite on the two player-facing pages ("the main public schedule and on the players personal schedule page"): double-booked should keep showing even once flagged `needs_sub`, since it's important information for other players and would resolve once someone actually claimed the sub slot. That version was built and verified (double-booked persists through `needs_sub`, clears itself once a sub actually claims the slot, since `findActualDoubleBookings()` already excludes `wa.status = 'subbed_out'`). Kyle then asked directly whether both badges could show at once — told no, it's if/else, only one badge renders — and, given that constraint, changed his mind back: **"let's go back to changing that status to 'needs sub' as that has more meaning for the other players than 'double booked'."** Final, current behavior (as of 2026-08-18): `schedule.ejs`, `lookahead.ejs`, and `me.ejs` all show the `double_booked` badge only while `a.status` is `scheduled`/`confirmed`; once a slot is flagged `needs_sub` (or resolves to `subbed_out`), the real status badge takes priority over double-booked. `admin/session_detail.ejs`'s per-player row was never reverted through this back-and-forth — it's shown `needs_sub` taking priority the whole time, since the admin already sees both facts via the week-level "sub open — `<name>`" badge and the session-level "Double-booked" summary card. `request_sub.ejs`/`swap.ejs` are unaffected either way since their underlying queries only ever pull `scheduled`/`confirmed` assignments; `dashboard.ejs`'s double-booked mention is a session-level count, not a per-player badge.

Verified live (both the `needs_sub`-priority version and the double-booked-persists version were independently confirmed against a seeded two-session scenario matching Kyle's repro, before he settled on `needs_sub`-priority as final): with a player double-booked and then flagged "needs a sub," `/schedule`, `/lookahead`, `/me/:playerId` show "needs sub" and the admin session detail's per-player row also shows "needs sub"; the other three players in that week show their correct "scheduled" badge throughout. If this area gets touched again, note the badge logic can only show one status at a time (if/else, not both) — that constraint is what settled the final direction.

### Per-session sub list: master list vs. who actually gets escalated to

Kyle, 2026-08-13: "Subs need to be unique to each session... each session needs to be able to pick the subs for that session that will get emailed if a player from the roster does not respond to a sub request." Before this, `broader_sub_list` was a single flat, global table — `escalateOverdueRequests()` fetched it once and emailed *everyone* on it for *every* session's overdue request, with no way to scope it down. For an install running multiple concurrent sessions (see "Overlapping-session double-booking guard"), that meant a sub who only actually plays Tuesdays would get emailed about a Thursday session's empty slot too.

New join table `session_sub_list` (`session_id`, `broader_list_id`, both `ON DELETE CASCADE`) sits between `sessions` and `broader_sub_list` — `broader_sub_list` itself is unchanged and still the single master pool of "people willing to sub at all" (add/remove at `/admin/sub-list`, unchanged). `subFlow.js`'s new `sessionSubList(sessionId)` resolves a session's own subset; `escalateOverdueRequests()` now calls it *inside* its per-request loop (not hoisted above, since different open requests can belong to different sessions with different lists) instead of reading the master list once. A session with zero subs assigned behaves exactly like the old "master list is empty" case did — the request goes straight to `unfilled` instead of `escalated`, no emails sent.

**Backward compatibility for existing installs, handled in `db/index.js`:** every session used to implicitly escalate to the entire master list, so upgrading with `session_sub_list` completely empty (untouched) but real `sessions`/`broader_sub_list` rows already present would otherwise silently stop all escalation emails for every session until the admin manually re-assigned people. A one-time seed (same "only if the table is empty" pattern as the `admins` seed below) populates the full cross-product — every existing session × every existing master-list person — exactly once, so upgrading preserves current behavior; only new sessions created after the upgrade start with an empty (deliberately-opt-in) sub list. A brand new install has no sessions or master-list rows yet, so this seed is a no-op there.

**UI:** `GET/POST /admin/sessions/:id/subs` (new "Manage subs" button on `session_detail.ejs`, next to "Manage blackout dates") renders the *entire* master list as a checkbox checklist, pre-checked for whichever are currently assigned to this session — same delete-then-insert-on-save pattern as the blackout-dates page, so removing a checkbox just means "not saved back in," nothing to explicitly delete-guard against. The master `/admin/sub-list` page also gained an "Assigned to" column (which sessions currently include each person, linking to that session's `/subs` page) purely for visibility, since a person could otherwise be assigned to several sessions with no way to see that from the master list alone.

**Scope:** regular sessions only in practice — ad-hoc sessions never create `sub_requests` rows at all (no confirm/need-a-sub flow, see "Ad-hoc sessions"), so `escalateOverdueRequests()` never reaches one regardless of what's assigned to it. The `/subs` page isn't blocked for an ad-hoc session (no link to it from `adhoc_session_detail.ejs`, but the route itself doesn't check `session_type`) — assigning subs there is simply inert, not harmful, so it wasn't worth the extra special-casing.

### Cron is an in-process interval loop, not `node-cron`

`src/services/cron.js` runs a plain `setInterval` every 60s (`start()`/`tick()`), not a cron-string library, because match time / reminder time / follow-up time are all per-session admin-configurable rather than fixed. Every check is phrased as "should this have already happened?" (compare `now` against a computed threshold) rather than "is it this exact instant?", so a missed tick (e.g. the Pi rebooting overnight) still catches up correctly once the process is back up — this is why `start()` calls `tick()` immediately on boot in addition to the interval.

All wall-clock-to-UTC conversion goes through `src/services/tz.js`'s `zonedTimeToUtc()`, which uses `Intl.DateTimeFormat` to resolve the IANA timezone stored in `app_settings` (a single global row, not per-session) into a real UTC instant, handling DST correctly. `match_time`/`reminder_time` in the `sessions` table are naive `'HH:MM'` wall-clock strings with no timezone of their own — never compare them with raw SQLite `datetime()` math (there's precedent for this being a real, shipped bug — see git history / the escalation timing fix); always route through `zonedTimeToUtc`.

Dedup for reminder-ish emails is done by checking `email_log` for an existing row (`category` + `related_week_id` + `to_email`) rather than a boolean flag, which is what makes it safe for the admin's manual "Send reminders now" button (`cron.sendRemindersNowForWeek`) to share the exact same `sendReminderEmailsForWeek` function as the automatic path — calling it twice never double-sends.

`cron.processWeekLocking()` was added after a real bug: `weeks.locked` existed in the schema and every consumer of it — `session_detail.ejs` hiding edit buttons for completed weeks, `runScheduler()` skipping locked weeks when regenerating — was already written correctly, but *nothing* ever set `locked = 1`, so those checks were silent no-ops. In practice this meant re-running "Schedule these players" after any match had already happened would wipe and regenerate that match's real assignments/confirmations right along with the actually-open future weeks. `processWeekLocking()` runs every tick and sets `locked = 1` on any week whose `matchAt` (same timezone-aware computation as follow-ups/escalations) has passed, and also calls `tokenStore.invalidateTokensForWeek()` for that week, so a reminder or follow-up email a player never opened can't be used after the fact to "confirm" or "need a sub" for a match that already happened. If you're touching scheduling or the admin week-detail view, this is the thing that makes "locked" real — don't reintroduce a path that skips either the lock or the token cleanup.

### Email log has a real status, not a subject-line hack

`email_log.status` is `'sent' | 'failed' | 'logged_dev_mode'` (the last one meaning no `GMAIL_USER`/`GMAIL_APP_PASSWORD` configured, so the email was only printed to the console — this is the normal case in local dev). All sending goes through `src/services/email.js`'s `sendMail()`, which always writes a log row regardless of whether SMTP is configured, so the admin Email Log page (`/admin/email-log`) works identically in dev and production.

### "My Page": a bookmarkable per-player dashboard

### Direct player-to-player swaps

Added 2026-08-11, after a design conversation with Kyle up front (self-service, requires the other player's confirmation, two-way trade rather than a targeted one-way sub — see swapFlow.js's own doc comment for the full rationale). Distinct from the existing sub-request flow (`subFlow.js`'s `sub_requests`/`sub_offers`, a one-to-many fan-out where someone drops out and anyone can claim it): a swap is addressed to exactly one specific player, and it's a trade, not a departure — neither player becomes `is_sub`, since each is still playing their own configured number of games, just on a different date. New `swap_requests` table (single token per row, like `sub_offers`, but exactly one recipient instead of a fan-out).

`src/services/swapFlow.js` is the service layer: `eligibleOwnAssignments()` (a player's own upcoming, swappable weeks — step 1 of the self-service picker), `eligibleTargetAssignments()` (given a chosen own-week and a target player, which of *their* weeks could actually be traded for it), `proposeSwap()`, `respondToSwap()` (accept/decline), and `adminCancelSwap()`. Eligibility excludes locked weeks, anything already mid-flow (an open sub request or another pending swap touching either assignment), same-week pairs (nothing to trade), and — critically for self-service, since there's no admin around to override — blocks a trade that would land either player on a date they've already blacked out, or that would collide with a week either player already has a (different) slot in.

**The accept-time re-validation gotcha, and how it's handled:** `respondToSwap()` re-checks eligibility at the moment of acceptance (state may have moved since the proposal was created), reusing the same `isAssignmentSwappable()`/`eligibleTargetAssignments()` functions the picker itself uses. Naively, this breaks: those functions treat *any* pending swap touching an assignment as "already mid-flow" and refuse it — including the very swap request being accepted, since it's still `status = 'pending'` right up until the transaction that accepts it. Both functions take an `excludeSwapRequestId` parameter for exactly this: `respondToSwap()` passes the current request's own id so it doesn't see itself as a blocking conflict, while every other caller (a brand-new proposal) passes nothing, so any *other* in-flight swap on either assignment still correctly blocks it. This was caught by a live test during verification, not by inspection — worth remembering if this logic is ever touched again.

**What actually happens on accept:** a transaction swaps which `player_id` each existing `week_assignments` row belongs to (the week, court, and team stay put), sets both to `confirmed`, and invalidates old tokens on both assignments (same reasoning as `subFlow.js`'s claim/create-sub-request — a stale reminder link shouldn't be able to act on behalf of whoever just traded out of that slot). Ball duty is deliberately untouched — it stays attached to the week, not the player, same as every other roster-changing action in this app (see "Understaffed weeks" → "Filling an understaffed week manually" above) — so a swap can leave ball duty pointing at someone who no longer plays that week; visible and fixable from the session detail page like any other week, not auto-handled here.

**Cross-session double-booking, flagged not blocked:** Kyle's explicit call — if an accepted swap happens to land a player on a date they're already playing in a *different* session, don't block the swap (the two players already agreed to it), just flag it for the admin to fix manually. `sessionHelper.js`'s `findActualDoubleBookings()` is a new, more concrete cousin of `findOverlappingSessionEnrollments()`: that one flags players merely *enrolled* in two colliding sessions (a risk); this one finds a player *actually assigned* to play in two different non-archived sessions on the exact same calendar date (a confirmed conflict), regardless of how it happened — a swap, an admin reassign, anything. It's a live, computed-at-render-time query, not a stored flag, so fixing either assignment makes it disappear on its own next render. Surfaced in the same three places as the overlap-enrollment warning: a "Double-booked" card on session_detail.ejs, a dashboard flag, and the Status page — all styled more urgently than the enrollment-level warning, since this one is confirmed, not a risk.

**Player-initiated activity logging:** Kyle asked that swaps show up in the same Activity Log as everything else, even though players (not admins) trigger them and there's no admin session in scope. `activityLog.js`'s `logPlayerActivity({ playerName, action, description, sessionId })` writes to the *same* `admin_activity_log` table with `admin_id = NULL` and `admin_name` stamped as `"<player> (player self-service)"`, so it's unmistakable in the log which rows were a player acting on their own behalf versus an admin. `logActivity()` (admin-initiated) is untouched; this is purely additive. Every swap email (`swap_request`, `swap_proposed_self_notice`, `swap_declined`, `swap_accepted`, `swap_group_notice`) also goes through the same shared `sendMail()` as every other email in the app, so `email_log` captures all of them automatically — no separate logging path was needed for that half of Kyle's request.

**Discoverability:** a nav link (`/swap`, mirrors Request a Sub's player-picker pattern), a "Propose a swap" action next to "Need a sub" on each upcoming assignment on My Page (`/me/:playerId`), and — like every other token-driven result page — a "My Page" link on the accept/decline confirmation screen.

**Identity-drift guard at accept time — a real bug found by scenario testing, not a hypothetical:** Kyle asked (2026-08-11) for the swap eligibility logic to be tested against every scenario, including "an admin reassigns one side of a pending swap before it's accepted." That race turned up a genuine bug: `respondToSwap()`'s re-validation (`isAssignmentSwappable`/`eligibleTargetAssignments`) only ever checks whether an assignment *row* is still swappable — locked, right status, nothing else mid-flow — it never checked whether the row still belongs to the *player* the request actually named. If an admin used Reassign on either assignment for an unrelated reason while the swap sat pending (the row id doesn't change, so every other check still passed), the original recipient could click their still-live accept link and the code would silently execute a trade with whoever now occupied that seat instead — a player who never saw the proposal, never clicked anything, and had no idea a swap happened. Verified live: proposed Alice-for-Carol, admin-reassigned Carol's slot to Bob, Carol accepted her original email link, and the trade went through as Alice-for-Bob.

Fixed by snapshotting `swap_requests.initiator_player_id` (new column, alongside the pre-existing `target_player_id`) at `proposeSwap()` time, and having `respondToSwap()` compare both stored ids against `getAssignmentContext()`'s *current* occupants before doing anything else — a mismatch on either side fails closed with `no_longer_available`, the same reason code already used for every other accept-time eligibility failure. A pre-migration row has `initiator_player_id = NULL`, which can never equal a real player id, so it also fails closed rather than skipping the check. Verified in both directions (target-side reassign, initiator-side reassign) and confirmed the legitimate accept path (nothing reassigned) still works normally.

Since this check alone would leave the *other*, uninvolved player's still-pending `swap_requests` row silently doomed to fail whenever they eventually click accept — no signal to the admin that it happened, no cleanup — `POST /sessions/:id/weeks/:weekId/reassign` also now calls `swapFlow.adminCancelSwap(assignment.id)` up front (same spot it already calls `subFlow.closeActiveSubRequestForAssignment`), so reassigning a slot with a pending swap on it cancels that swap outright and says so in the flash message, rather than leaving a dead-but-still-"pending" row for the identity-drift check to catch later.

**Overdue-swap nudge + expiry:** Kyle asked (2026-08-11) what happens if the target player just never responds to a swap proposal, and whether it's flagged anywhere. It wasn't — a pending swap had no timeout, no follow-up nudge, and no dashboard/status visibility at all, unlike `sub_requests` (which escalates to the broader list 24h before match and gets flagged `unfilled` once match time passes). Two new cron entry points in `swapFlow.js`, both called from `cron.js`'s `processEscalations()` alongside the existing sub-request escalation:

- `nudgeOverdueSwaps()` sends exactly one reminder email to the target player once within 48 hours of whichever of the two involved weeks' matches comes first (double the sub-request lead time, since this is a one-to-one negotiation rather than a fan-out with more chances to fill). Mints a second, additionally-valid token (`swap_requests.nudge_token`, hashed like `token`) rather than rotating the original — same "don't kill a link that's already out" reasoning as `tokenStore.js`'s multiple-valid-tokens fix for reminders. `findSwapRequestByToken()` checks both columns, used by both the GET landing page and `respondToSwap()` itself so there's exactly one place that knows about the two-token shape. Dedup is via `nudged_at` (set the first time, checked before sending again) rather than `email_log`, since a swap request is already its own single-recipient row with a clear lifecycle — no fan-out to dedupe across.
- `expireStaleSwaps()` marks a still-`pending` request `'expired'` once that same earliest-match threshold actually arrives (the trade can't happen anymore either way — the earlier week's lock already blocks it via `isAssignmentSwappable()`). This isn't just cosmetic: `isAssignmentSwappable()` treats *any* `pending` swap as blocking *both* of its assignments, including the side whose own week hasn't locked yet — without this, a swap that goes stale on one side would permanently prevent the target player's *other*, unrelated slot from ever being swapped again with anyone, since nothing ever moved the request out of `'pending'`. Found and confirmed via live scenario testing (2026-08-11), then fixed by this same expiry mechanic — verified the previously-permanently-blocked assignment becomes swappable again immediately after expiry. No email is sent for expiry itself (silent bookkeeping, same as `processWeekLocking()`/`flagStillUnfilled()`) — the nudge+flag already covered visibility while it was still actionable; once expired there's nothing left to decide.

Both are gated on `archived_at IS NULL` (same reasoning as every other cron pass) but deliberately **not** gated on `reminders_enabled` — like sub-request escalation, this is "is this negotiation stuck" rather than a routine reminder, so the per-session pause toggle shouldn't silence it.

**Dashboard/Status visibility:** a `pending` + already-`nudged_at`-set swap is the swap equivalent of `unfilledSubs` — surfaced as a per-session dashboard flag (`admin.js`'s dashboard route, `staleSwaps` count) and flattened with specifics on the Status page (`statusPage.js`'s `getAttentionItems().staleSwaps`: who proposed what, which two dates, when it was nudged). Both are live, computed-at-render-time queries filtered on `status = 'pending'`, so the flag clears itself the moment the swap resolves (accepted/declined/cancelled) or expires — no separate dismiss action needed, consistent with every other self-clearing flag in this app. `session_detail.ejs`'s existing "swap pending" badge gains a `(nudged)` suffix once `nudged_at` is set, so it's visible in context too, not just in the aggregate counts.

### Admin activity log: who did what, since every admin has full access

Added 2026-08-10 for accountability — `admins` has no permission tiers (any admin can do anything, per "Admin accounts" below), so once there's more than one admin, "who changed this?" was otherwise unrecoverable. `admin_activity_log` (`id`, `admin_id`, `admin_name`, `action`, `description`, `session_id`, `created_at`) is a plain, human-readable audit trail — one row per action with a prose `description` — deliberately matching the existing `email_log` pattern (simple, queryable, no structured before/after diff system) rather than a heavier audit framework, since this is a small, low-volume admin panel.

`src/services/activityLog.js` exports `logActivity(req, {action, description, sessionId})`, called at the point of the actual mutation in each `admin.js` route. `admin_name` is a denormalized snapshot taken at write time (read from `req.session`, set at login) rather than joined from `admins` at read time, so the log still reads correctly even if that admin is later renamed or deactivated. `session_id` is nullable (admin account management and global settings changes aren't tied to a session) and, like `email_log.related_week_id`, is deliberately **not** `ON DELETE CASCADE`'d — a change record should outlive a deleted session for history purposes — so `POST /sessions/:id/delete` nulls it out first, same pattern it already uses for `email_log.related_week_id`.

**What's logged:** session create/update/delete/archive/unarchive, "Schedule these players" runs (both success and failure), reassign, mark-confirmed, clear-sub-request, add-player (understaffed-week fill), ball duty assignment, admin-side blackout edits, player create/edit/deactivate/activate, broader-sub-list add/remove, admin account create/deactivate/activate/reset-password (never logs the password value itself), and timezone changes (only when the value actually changed).

**What's deliberately not logged, and why:** the admin's manual "Send reminders now" / "Resend link" actions and `POST /email` (custom email) — these are already fully captured in `email_log` (recipient, subject, category, timestamp), so a second log entry would just be noise pointing at the same event. Backup creation/deletion isn't logged either — it's infrastructure housekeeping, not a change to scheduling/roster state, and `src/services/backup.js` already timestamps files on disk. If any of these ever need a "who clicked this" trail beyond what they already have, follow the same `logActivity()` call-site pattern rather than inventing a new mechanism.

**Viewing it:** `GET /admin/activity-log` (nav link next to Email Log) — filterable by session, action tag, admin, and a free-text search over `description`, most recent first (last 300 rows), following the exact same filter-form/table layout as the Email Log page.

### Custom email: one player, or a whole session's roster

Kyle, 2026-08-13: the existing `Admin → Send Email` page could only address one player at a time — no way to message everyone currently scheduled in a session (e.g. "practice moved to next court over this week") without sending it one-by-one. `admin/custom_email.ejs` now has a `recipient_type` radio (One player / Whole session roster) toggling between the original player `<select>` and a new session `<select>`, same JS-toggle pattern as `session_form.ejs`'s regular/adhoc fields.

`POST /admin/email` branches on `recipient_type`: the session path looks up the chosen session's roster with the exact same query used everywhere else in this app for "who's the roster" (`session_players` joined to `players`, `active = 1` — the same shape `ensureInvitesForWeek()` and the blackout-notify route use), then calls `email.sendCustomEmail()` once per player — so `email_log` ends up with one row per recipient, same as any other fan-out in this app, nothing new to reconcile. An empty roster flashes an error and sends nothing rather than silently no-op'ing. Both regular and ad-hoc sessions are selectable (ad-hoc's `session_players` is its invite list, so "roster" means the same thing there too), and archived sessions are included in the dropdown (labeled) rather than hidden — this is a deliberate one-off admin action, not an automatic pass, so it doesn't need to respect archiving's "go fully quiet" rule the way cron-driven emails do.

`sendCustomEmail()` gained an optional `session` param (default `null`, so the original single-player call site is untouched and still renders plain with no club/court context). When present, it's threaded into `sendMail()` (club-name subject prefix) and prepended with `matchBanner(session, null)` — the same no-single-date banner treatment the swap templates use, since a whole-roster message isn't tied to one match either. Not logged to the admin activity log, consistent with the existing "already fully captured in email_log" reasoning above.

### Match-day email subjects include time + court, via timeAndPlace()

`email.js`'s `timeAndPlace(session)` returns `"6:00 PM, Court 3"` (or just `"6:00 PM"` if the session's `court_info` is blank), and is spliced into the subject line — not just the body — of every email tied to one specific match: `sendConfirmationReminder`, `sendFollowUpReminder`, `sendSubRequestOwnConfirmation`, `sendSubRequestFanout`, `sendEscalationEmail`, `sendSubFilledNotice`. This is independent of, and in addition to, the club-name prefix `sendMail()` already adds and the club/court line `footer()` already puts in the body — three separate things that all happen to draw from the same `session.club_name`/`session.court_info`/`session.match_time` fields. `sendBlackoutConfirmation` and `sendCustomEmail` deliberately don't call `timeAndPlace()` — neither is about one specific match/time, so there's nothing meaningful to put there. If you add a new match-related email template, follow the same pattern: `${fmtDate(week.match_date)}, ${timeAndPlace(session)}` somewhere in the subject.

### Email body font size: wrapped centrally in sendMail(), not per-template

Every email template built its `html` as raw `<p>`/`<a>`/`<ul>` fragments with no `font-size` set anywhere on the body content — only `footer()`'s club/court and "Full schedule" lines were ever explicitly sized (12px, deliberately small/secondary). That meant every email's actual body text rendered at whatever an unstyled `<p>` defaults to in the recipient's mail client, which reads noticeably small in several common clients, particularly Gmail's mobile app. Kyle, 2026-08-12: "I feel like the font is too small in the body of the email when sending out reminders and confirmation emails."

Fixed once, centrally, rather than touching every template: `email.js`'s `wrapEmailHtml(innerHtml)` wraps the finished `html` in a single `<div>` with an inline `font-family`/`font-size:17px`/`line-height` (inline styles are the only thing reliably honored across mail clients — many strip `<style>` blocks entirely), applied inside `sendMail()` right before the actual `nodemailer` send. Every template is untouched — they still build plain `<p>` fragments same as before — so this can't drift out of sync template-by-template, and any new template automatically inherits the fix for free just by going through `sendMail()` like everything else already does. `footer()`'s smaller 12px lines still render smaller than the new 17px body, since an inline style on a child element always wins over the inherited size from the wrapping `<div>`. The CTA buttons (Confirm, Need a sub, I'll play, etc.) never had their own explicit `font-size` either — they now inherit the new 17px from the wrapper too, which reads as a comfortable, easily-tappable button size rather than a side effect worth calling out separately.

### Club name/court info: per-session, not global — mind the vestigial app_settings columns

`sessions.club_name`/`sessions.court_info` (free text) drive the subject-line prefix and footer line on every email, since a single install can run sessions for different clubs/courts. This used to be one global value in `app_settings`; `src/services/email.js`'s `sendMail()`/`footer()` both take a `session` argument now (nullable — `sendCustomEmail()` has no session context and passes `null`, which just omits the prefix/line) instead of reading a getter. **Every template function in `email.js` must thread its `session` param through to both `footer(session)` and the `sendMail({..., session})` call** — it's not read from anywhere else. `db/index.js`'s migration backfills every existing session from the old `app_settings.club_name`/`court_info` on the boot where the new `sessions` columns first get added, guarded by `hasColumn()` so a fresh install (whose `schema.sql` no longer creates those `app_settings` columns at all) doesn't try to read a column that was never there. Existing installs keep the old, now-unused `app_settings.club_name`/`court_info` columns sitting around after that one-time read — consistent with this app's additive-only migration philosophy (see the guard pattern above), nothing ever drops a column.

### Session naming: `name` is the admin's internal label; player-facing pages show club/court too

Kyle flagged (2026-08-11) a real source of confusion: `sessions.name` is a single field used both on the admin dashboard *and* every player-facing page (the session picker dropdown, `/schedule`/`/lookahead` headers, the PDF, calendar events) — so a name that makes sense to the admin internally (e.g. two similarly-named sessions for bookkeeping purposes) doesn't necessarily tell a player which physical court/session they're looking at, especially when the same player is enrolled in two sessions at the same club on the same day of week (his example: Frontenac Tennis Club, Court 2 on one Wednesday session and Court 4 on another).

Considered adding a separate player-facing "display name" field, but Kyle chose the simpler option: no new field to maintain — `email.js`'s `sessionPublicLabel(session)` derives `"Session name — Club, Court"` directly from the existing `club_name`/`court_info` fields (falls back to the bare name if neither is set), so it can never drift out of sync with the real court the way a hand-typed second name field could. Wired into `app.locals` in `app.js` (same pattern as `fmtDate`/`fmtTime`) so every EJS template can call it directly with no explicit passing required. Used everywhere a player currently sees a bare session name: `partials/session_picker.ejs`'s dropdown (covers every page that includes it — schedule, lookahead, PDF, blackout, calendar, swap, request-sub), `schedule.ejs`/`lookahead.ejs` headers, `pdf.js`'s on-page header text (not the downloaded filename, left as the bare name — sanitized to underscores anyway, not worth the churn), and `ics.js`'s calendar event titles (both `buildPlayerICS` and `buildPlayerFeedICS`). **Deliberately not used on any admin-facing page** (dashboard, session detail/edit, stats, activity log, email log, status page) — those keep showing the admin's own internal `name` unchanged, since that's the organizational label that makes sense in that context and Kyle didn't want it cluttered with club/court repeated everywhere he already knows it.

**Email subjects were a related, partially-pre-existing gap.** `timeAndPlace(session)` (time + court) was already spliced into the subject line of 7 templates tied to a specific match (reminder, follow-up, sub request/escalation/filled, swap group notice) — see "Match-day email subjects include time + court" below — so those already disambiguated two same-day, same-club sessions correctly, since `match_time`/`court_info` are session-level fields, not per-week, so `timeAndPlace()` is valid to add anywhere regardless of which specific date a subject is about. But 5 direct-swap templates (`sendSwapRequestEmail`, `sendSwapNudge`, `sendSwapProposedConfirmation`, `sendSwapDeclinedNotice`, `sendSwapAcceptedNotice`) and `sendBlackoutNotice` only had the club name (via `sendMail()`'s prefix) and the bare session name — no time/court — so a player enrolled in two same-day Frontenac sessions genuinely couldn't tell which court a swap invite was about from the subject alone. All 6 now also splice in `timeAndPlace(session)`, e.g. `"Frontenac Tennis Club — Alice wants to swap weeks with you — Session A, 6:00 PM, Court 2"`. Verified end-to-end against Kyle's exact two-session scenario — every subject for a Court 2 session mentions Court 2, every Court 4 one mentions Court 4, no subject conflates the two.

### Session color: a second, faster disambiguator on top of sessionPublicLabel

### Routes and views

`src/routes/public.js` (no auth) and `src/routes/admin.js` (everything after `router.use(requireAdmin)` requires a password-gated session cookie) are mounted in `src/app.js`. Admin routes use a simple `req.session.flash = {message, type}` / `popFlash()` pattern (see top of `admin.js`) for post-redirect messages — follow that convention for new admin actions rather than inventing a new one.

EJS views have no shared layout engine — instead `app.locals.fmtDate`/`app.locals.fmtTime` are set once in `app.js` so every template can call them directly, and each page manually does `<%- include('partials/header', {title}) %> ... <%- include('partials/footer') %>` (admin views use `partials/admin_header` instead, which also renders the flash message). `partials/session_picker` is a shared dropdown used by every public page that operates on "the current session" (`src/services/sessionHelper.js`'s `resolveSession()` resolves it from `?session=` or falls back to the most relevant active/scheduled session) — multiple concurrent sessions are supported by design, so don't assume a page only ever has one session in scope.

### Admin accounts: password-only login, DB-backed since multi-admin

`admins` (name, email, password_hash, active) replaced the old single `ADMIN_PASSWORD_HASH`-in-`.env` model. The login form still only asks for a password (no username) — `auth.js`'s `findAdminByPassword()` checks the candidate against every *active* admin's own bcrypt hash and returns whichever one matches, so each person still has a distinct, individually-revocable password without adding a username field to the UI. `db/index.js` seeds a single `Admin` row from `ADMIN_PASSWORD_HASH` on first boot if the table is empty, so upgrading an existing install doesn't invalidate anyone's password; `.env`'s `ADMIN_PASSWORD_HASH` is never read again after that. `POST /admin/admins/:id/deactivate` refuses to drop the last active admin (would lock everyone out) and self-deactivation immediately ends the current session. There are no permission tiers — any admin can do anything.

### Backups: VACUUM INTO, not a raw file copy

`src/services/backup.js` uses SQLite's `VACUUM INTO` (via a fresh read-only `DatabaseSync` connection) rather than copying `data/tennis.db` directly. `db/index.js` runs in WAL mode, so recently-committed rows can still be sitting in `data/tennis.db-wal` and not yet in the main file — a plain `cp` while the app is running can silently produce a backup missing recent data. `VACUUM INTO` reads through SQLite's own consistent snapshot instead, so it's safe at any time without stopping the app. Filenames include milliseconds (`createBackup()` retries on collision up to 5 times) because `VACUUM INTO` refuses to overwrite an existing file, and two backups fired in quick succession — e.g. a double-clicked "Create backup" button — would otherwise collide on a same-second timestamp. `src/scripts/backup-db.js` is the cron entry point (`npm run backup`); the admin route (`POST /admin/backup`) calls the exact same `createBackup()`/`pruneBackups()` functions, so there's one code path for both. `GET /admin/backup/download/:filename` validates the filename against `isValidBackupFilename()`'s strict regex before touching the filesystem, since it's a user-facing route that takes a filename straight from the URL.

### Dark mode: CSS custom properties + `data-theme`, no framework

`src/public/css/style.css` defines every color as a CSS custom property on `:root`, re-declared under `[data-theme="dark"]`. There's no separate dark stylesheet — the same rules apply in both modes because every color reference in the file goes through `var(--...)` (never a raw hex outside the two `:root`/`[data-theme="dark"]` blocks). When adding new CSS, always reach for an existing variable (or add a new one to both blocks) rather than hardcoding a color, or it'll look identical in both themes and wrong in one of them.

The theme itself is just an attribute on `<html>`. Each page's `<head>` (in `partials/header.ejs`, `partials/admin_header.ejs`, and standalone `admin/login.ejs`) has a small blocking inline `<script>` that reads `localStorage.getItem('theme')` (falling back to `prefers-color-scheme`) and sets `data-theme` *before* the stylesheet paints, so there's no light-then-dark flash on load. The actual toggle button (`#theme-toggle`, present in both header partials) is wired up by `src/public/js/theme.js`, loaded with `defer` — it just flips the attribute and writes the choice back to `localStorage`. Because it's plain `localStorage` in a real browser (not a Claude-rendered artifact), this is fine here, unlike the no-localStorage rule that applies to Claude.ai artifacts.

### Personal calendar: one-time download vs. subscribable feed

`src/services/ics.js` has two generators, both wrapping the `ics` npm package's `createEvents`, deliberately kept separate rather than one function with a mode flag — they differ in scope (one session vs. every session a player's in) and, more importantly, in the one detail that makes a subscription actually behave like a subscription (see below), which only matters for one of them.

`buildPlayerICS(playerId, sessionId)` — the original, used by `GET /calendar/download` — is a one-time file for a single selected session. `res.setHeader('Content-Disposition', 'attachment; ...')` makes the browser save it immediately; if the schedule changes later (a re-schedule, a sub taking someone's slot), the downloaded file is now stale and the player has to know to come back and re-download it.

`buildPlayerFeedICS(playerId)` — added 2026-08-10, used by `GET /calendar/feed/:playerId.ics` — is a *subscribable* feed instead: every `scheduled`/`active`, non-archived session the player is currently enrolled in (mirrors `sessionHelper.js`'s `getViewableSessions()` scope), at a URL a calendar app fetches repeatedly on its own schedule rather than once. No `Content-Disposition: attachment` here — the point is for it to be added as a standing subscription, not saved as a file. Route path uses a `.ics` URL suffix (`/calendar/feed/:playerId.ics`) rather than a query param specifically because some calendar apps sniff the extension to decide whether a link is even subscribable.

**The detail that makes "subscribe" actually work:** the `ics` library generates a random `uid` per event when one isn't supplied. For a one-time download that's irrelevant — the file is generated once and that's the end of it. For a *repeatedly re-fetched* feed it would be a real bug: every refresh would hand the subscribing calendar app a full set of "new" events instead of updates to the ones it already has, so Apple/Google Calendar would accumulate duplicates forever instead of updating in place. `buildPlayerFeedICS` builds a stable, deterministic `uid` per event from `session id + match_date + player id` (`assignment-<sessionId>-<matchDate>-<playerId>@tennis-scheduler.local`), so the same real-world match always maps to the same UID on every fetch, and the app's own diffing does the right thing.

No token or auth on the feed URL (`?player=<id>`-style, guessable) — consistent with every other player-facing page in this app: a player's own schedule isn't sensitive (it's already visible on the public `/schedule` page to anyone with the link), and there's no login model to check against regardless.

`calendar.ejs` shows both options side by side: the existing session-scoped download form, and a new subscribe section with its own player dropdown (deliberately populated from *all* active players, not `session_players` for the currently-selected session — the feed spans every session a player's in, not just whichever one happens to be selected in the picker at the top of the page). Client-side JS builds two links once a name is picked: a `webcal://` link (same URL, scheme swapped — most calendar apps, notably Apple Calendar, treat `webcal://` as "open my subscribe flow" rather than "download") for a one-click `Subscribe` button, and the plain `https://` URL as copyable text underneath for apps (Google Calendar on desktop) that want "Add calendar → From URL" instead of a clickable scheme handler.

Calendar apps decide their own refresh interval for a subscribed feed — the `ics` library's default `X-PUBLISHED-TTL:PT1H` is only a hint, and several major clients (Google Calendar in particular) ignore it and poll on a much longer cycle they don't expose as configurable. `calendar.ejs` says so explicitly rather than promising real-time updates.

### Multi-court sessions: players_per_week must be a multiple of 4

`sessions.players_per_week` can be more than 4 (2 courts = 8, 3 courts = 12, ...), and `week_assignments.court` (1-indexed) records which physical court a given team pair is on for that week. This replaced a real, serious bug: the engine's team-splitting used to destructure exactly 4 players out of whatever roster it was handed (`const [a, b, c, d] = four`), so any week with more than 4 players silently dropped everyone past the first 4 from `teamA`/`teamB` — they'd still consumed a target-game slot in the max-flow solution, but never got a `week_assignments` row, a confirmation email, or a calendar entry. `engine.js`'s `splitIntoCourtTeams()` now chunks a week's roster into groups of 4 and splits each independently (courts are disjoint by construction — every player is on exactly one court — so there's no cross-court interaction to account for). `solveAssignment()` rejects a non-multiple-of-4 `playersPerWeek` up front as an `invalid_players_per_week` conflict rather than silently truncating; `admin.js`'s `invalidPlayersPerWeek()` also validates this server-side on session create/update so a bad value never reaches the engine in the first place.

Anywhere that reads `week_assignments.team` to group players into pairs (session_detail.ejs, schedule.ejs, lookahead.ejs, pdf.js, the admin stats partner matrix) has to key by `(week, court, team)`, not just `(week, team)` — otherwise "Team A" on court 1 and "Team A" on court 2 get merged as if they were the same pair. `engine.test.js` Test 5 is the regression test for the original bug (asserts every player in a multi-court week ends up on some court's team, not just the first 4); Test 6 checks the new validation.

### Ad-hoc sessions: a second session shape, first-come-first-served pickup games

`sessions.session_type` (`'regular'` | `'adhoc'`, additive column, default `'regular'`) is fixed for the life of a session — set once at creation (a radio choice on the New Session form, hidden once a session exists) and never changed by any update route. Everything downstream branches on it: the admin session detail route (`GET /admin/sessions/:id` in `admin.js`) renders a completely separate view (`admin/adhoc_session_detail.ejs`) for an ad-hoc session rather than threading `isAdhoc` conditionals through the already-large regular `session_detail.ejs`.

Requested by Kyle (2026-08-12) after describing exactly how he already runs pickup games by hand: an invite email goes out to a roster ~56 hours before match time, first 4 to click get the first court, a 5th starts a new group waiting on 3 more, sometimes 8+ sign up before any reminder is needed; if sign-ups aren't a clean multiple of 4 by ~30 hours out he sends a reminder to stragglers; ~24 hours out he sends a final "here's who's playing" email. Explicitly **no** connection to blackout dates, cross-session double-booking checks, or the confirm/need-a-sub flow — "just sending email to see if players want to pick up another game during the week."

**The model.** An ad-hoc session still has the same recurring shape as a regular one (day-of-week, start/end date range — `weeks` rows are generated the identical way, via `scheduleRun.js`'s `ensureWeeksExist()`, reused as-is). What's different: no `target_games` fairness math, no blackout dates, no confirm/need-a-sub email flow, no ball duty rotation. Instead:

- **Roster** — `session_players` is reused as the ad-hoc invite list (not the regular roster), but `target_games` is always stored as `0` and ignored; managed via a simple add/remove checkbox list (`saveAdhocRoster()` in `admin.js`) rather than the target-math table, editable at any time (no draft/locked-in enrollment step to begin with, since ad-hoc sessions skip `draft` and start directly at `status = 'active'`).
- **Sign-ups** — a new `adhoc_signups` table (one row per roster player per week, created when the invite fires) tracks a hashed single-use `token` and a `signed_up_at` timestamp. That timestamp **is** the first-come-first-served order — `adhocFlow.js`'s `courtGroupsForWeek()` live-computes (never stores) how sign-ups chunk into complete groups of 4 (in formation order) vs. a single trailing incomplete group, same "live query, not a stored flag" pattern as `sessionHelper.js`'s `doubleBookingMapForSession()`.
- **Finalization** — `adhocFlow.js`'s `finalizeWeek()` materializes every currently-complete group into real `week_assignments` rows, status `'confirmed'` directly (signing up already *is* the player's confirmation — there's no separate confirm step for ad-hoc). Once a week has any `week_assignments` rows it's considered finalized and left alone on every later call — idempotent, so cron can safely re-check a week every tick.

**Cron timing (`cron.js`).** Three new passes, each keyed off one of three per-session lead-hour fields (`adhoc_invite_lead_hours`/`adhoc_reminder_lead_hours`/`adhoc_final_lead_hours` — nullable-free `INTEGER NOT NULL DEFAULT 56/30/24`, editable per session, validated server-side to count down in that order via `invalidAdhocLeadHours()`):
- `processAdhocInvites()` — at T-minus-invite-lead-hours, `ensureInvitesForWeek()` mints a token for every roster player who doesn't already have one and emails `sendAdhocInvite()`. Calls `ensureWeeksExist()` first since ad-hoc sessions have no "Schedule these players" click to have generated week rows already (same lazy-idempotent pattern `GET /blackout` uses for a draft regular session).
- `processAdhocReminders()` — at T-minus-reminder-lead-hours, only if there's currently something worth nudging about (nobody's signed up at all, or sign-ups leave an incomplete trailing group) — and only to roster players who haven't signed up yet. Mints a **second** token (`adhoc_signups.reminder_token`) rather than reusing the original: the original invite's raw token can't be recovered since only its SHA-256 hash was ever stored (same "don't kill a link that's already out" reasoning as `swap_requests.nudge_token`). `adhocFlow.js`'s `findSignupByToken()` checks both columns.
- `processAdhocFinalization()` — at T-minus-final-lead-hours, calls `finalizeWeek()` and emails `sendAdhocFinalRoster()` to everyone in a completed court (who's on it with them) or `sendAdhocNotEnough()` to anyone left in an incomplete leftover group. The leftover-group case has no `week_assignments` row to signal "already handled" the way a formed court does, so cron explicitly filters to `result_notified_at IS NULL` before emailing — otherwise a week that never fills a single court would re-send "not enough" on every tick forever.

All three are gated on `archived_at IS NULL` only — deliberately **not** on `reminders_enabled`, which is specific to the regular confirm/follow-up flow and has no ad-hoc equivalent.

**What's deliberately excluded, and where.** `sessionHelper.js`'s `getBlackoutViewableSessions()` filters to `session_type = 'regular'` (no blackout concept for ad-hoc). `resolveSession()` gained a `regularOnly` option, used by `GET /request-sub` and `GET /swap` in `public.js`, so an ad-hoc session never enters the pool those pages pick from (nothing to sub/swap out of with no fixed season roster). `me.ejs`'s per-assignment "Need a sub"/"Propose a swap" buttons are additionally suppressed per-row for `card.session.session_type === 'adhoc'`. `/schedule`, `/lookahead`, `/me`, `/calendar`, and the PDF are **not** filtered — once a court finalizes it shows up on all of those exactly like a regular-session match (real `week_assignments` rows, same queries), just with no sub/swap actions available on it.

**Admin session detail (`admin/adhoc_session_detail.ejs`).** Per week: the finalized courts if materialized, otherwise the live `courtGroupsForWeek()` breakdown (courts formed / waiting group / invited-but-not-signed-up) plus two manual-override forms — sign up a roster player immediately (`POST .../adhoc/signup`, covers "someone told me in person they're in," creating an `adhoc_signups` row on the spot if one doesn't exist yet) and withdraw one (`POST .../adhoc/withdraw`, blocked once the week has finalized — flashes an error rather than silently no-op'ing). **Known gap, not built:** once a week is finalized there's no dedicated UI to edit who's on a court (no ad-hoc equivalent of the regular session's Reassign flow) — narrow enough in practice (a firm pickup game roster isn't something that gets reshuffled the way a season-long one is) that it's noted here as a possible follow-up rather than built up front.

**Dashboard.** Regular and ad-hoc sessions get separate sections (`GET /admin`'s `sessions` query now filters `session_type = 'regular'`; a new `adhocSessions` list summarizes each session's next 4 weeks as "N court(s) filled" / "N waiting" / "finalized" / "no sign-ups yet" — no flags in the regular sense, since ad-hoc has no targets/blackout/confirm flow to flag).

Verified end-to-end in a live sandbox: full invite → 6 signups (1 court + 2 waiting) → stragglers-only reminder (3 recipients, not the 6 already signed up) → 7th signup → finalize at T-24h (4 `week_assignments` rows, all `status = 'confirmed'`, 4 final-roster emails + 3 not-enough emails) → re-running finalization sends zero further emails (idempotent). Live-rendered the New Session form (type toggle, lead-hour fields, roster checkboxes), created a real ad-hoc session end-to-end through the actual `POST /admin/sessions` route, confirmed the Edit page locks `session_type` to a fixed label with roster checkboxes pre-checked, confirmed the dashboard's new Ad-hoc sessions section, and confirmed creating a regular session and rendering the public `/schedule` page both still work with no regressions.

### Async route handlers: always wrap in asyncHandler

`src/middleware/asyncHandler.js` wraps every `async (req, res) => {}` route handler in both `routes/public.js` and `routes/admin.js`. Express 4 does not auto-catch a rejected promise from an async handler — a throw inside one becomes an unhandled promise rejection, which by default (Node ≥15) crashes the *entire process*, not just that one request, taking the whole site down for every player until something restarts it. `asyncHandler(fn)` forwards any rejection to `next(err)`, which lands in `app.js`'s existing error-handling middleware (renders a normal error page instead). `src/server.js` also registers `process.on('unhandledRejection'/'uncaughtException', ...)` as a last-resort net that logs and keeps the process alive — but that's a backstop, not a substitute for wrapping new async routes. Any new `async` route handler must be wrapped: `router.post('/x', asyncHandler(async (req, res) => {...}))`.

### PDF generation caveat

`src/services/pdf.js` uses PDFKit's standard fonts (WinAnsi encoding), which cannot render most Unicode symbols/emoji — they come out garbled. Use plain ASCII markers (e.g. `[!]`) for any in-PDF status indicators, not the Unicode characters used elsewhere in the EJS views/emails.

### Combined "all active sessions" PDF: one flat table by date, not one-page-per-session

Kyle, 2026-08-25: with more than one concurrent session running, printing each one's separate one-page PDF wasn't useful for "what's happening across everything this week" — he wanted one document covering every active session, "ordered by date so it fits on a couple of sheets of paper."

`pdf.js`'s `streamAllSessionsPDF()` (routed at `GET /pdf?download=all`) is a second, structurally different generator from `streamSeasonPDF()` above, not a mode flag on it — the two solve different problems. `streamSeasonPDF()` is always exactly one session, and shrinks font/row height as needed (down to a 10-22px row, 6-11px font floor) to force that one session onto a single page. `streamAllSessionsPDF()` instead uses a fixed, comfortable 9pt font and paginates naturally — `doc.addPage()` plus a re-drawn column header whenever the next row's `heightOfString`-measured height would overflow the current page — so a handful of concurrent sessions across a full season genuinely can run to two or three pages. That's the "couple of sheets" Kyle asked for, deliberately not one page of unreadably small text.

Pulls every session `sessionHelper.js`'s `getViewableSessions()` already considers viewable (status `scheduled`/`active`, not archived — the same scope the session picker and nav already use, ad-hoc sessions included once they've finalized a court, consistent with every other public page). Every `(week, court)` row from every session is flattened into one list and sorted purely by `match_date`, with `session.id` as a tiebreaker so two sessions sharing a date land as adjacent rows (grouped, not randomly interleaved) rather than by, say, club name. A week with zero assignments (not yet scheduled, or reduced to 0 by an understaffed week) is skipped entirely rather than printed as a blank row — a row that tells nobody anything works directly against "fits on a couple sheets" once multiplied across every active session's future weeks.

Since a single date can now span several different sessions, each row gets a small colored dot in the new "Session" column using the same `sessionColor()` every other page/email already uses for that session — the same "tell two sessions on the same day apart at a glance, not just by reading text" reasoning as the site's own session-switcher banner and match-day email banners (see "Session color" above). The `*`/`[!]`/`[DB]` legend from the single-session PDF is unchanged and still applies per-player.

Surfaced as a second button on `pdf.ejs`, labeled "Download All Active Sessions (PDF)" — only rendered when `sessions.length > 1` (the list `resolveSession()` already returns), since with only one active session it'd be identical to the existing single-session download and just adds clutter.

Verified live: seeded 3 concurrent active sessions (two sharing a Wednesday, one on Saturdays) across 8 weeks each — the generated PDF correctly interleaved all 24 rows by date, grouped same-date sessions together, and fit on a single page; a follow-up stress test with a 4th, 50-week session (74 total rows) correctly spanned 3 pages, each with its own repeated header and the legend landing only on the last page.
